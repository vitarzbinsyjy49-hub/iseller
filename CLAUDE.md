# AI Seller — контекст проекта

Telegram Mini App магазин техники (Apple, Dyson, PlayStation) + бот + канал.
Этот файл читается автоматически в начале каждой сессии. Держи его в актуальном
состоянии: он дешевле, чем заново раскапывать те же грабли.

## Деплой

```bash
bash update-server.sh
```

**Только из Git Bash.** Обычный `bash` в PATH уходит в WSL, а там нет SSH-алиаса
`iseller`. Скрипт сам делает pg_dump в `/opt/backups`, синхронизирует код,
пересобирает стек и проверяет health. Серверный `.env` **не перезаписывается** —
новые переменные добавлять на сервере вручную.

Деплой синхронизирует ВСЁ рабочее дерево. Незакоммиченные правки уедут в прод —
перед деплоем убедись, что в дереве только то, что должно там быть.

## Telegram — здесь самые дорогие грабли

**Сеть VPS режет Telegram в обе стороны.** Хостер (HOSTKEY) подтвердил:
региональное ограничение, снимать не будут. Поэтому:

- исходящие идут через **Cloudflare WARP** в режиме proxy → `TELEGRAM_PROXY_URL=socks5://172.18.0.1:40000`;
- WARP слушает только на `127.0.0.1`, до контейнера его дотягивает systemd-юнит
  `warp-docker-bridge` (socat на `172.18.0.1` — адрес хоста внутри docker-сети,
  из интернета недоступен);
- **вебхук не работает** — входящие от Telegram до нас не доходят. Бот живёт на
  **long polling**, сервис `bot` в `docker-compose.prod.yml`. Вебхук-роут в коде
  остался рабочим на случай, если фильтрацию когда-нибудь снимут.

Адрес `172.18.0.1` — шлюз docker-сети `techshop_default`. Обычный деплой его не
меняет, но при пересоздании сети (`compose down` + `up`) подсеть может стать
другой — тогда правь юнит и `.env`.

**Экземпляр бота строго один.** Два параллельных `getUpdates` по одному токену
Telegram отвергает с 409 Conflict.

### Кнопки в канале

`web_app`-кнопки Telegram разрешает **только в личном чате с ботом**. В канале
сообщение с такой кнопкой отвергается ЦЕЛИКОМ (`BUTTON_TYPE_INVALID`) — то есть
пост просто не публикуется. В канале только `url`-кнопки: ведут на
`t.me/<bot>?start=<payload>`, бот ловит payload и открывает нужный экран Mini App
уже настоящей web_app-кнопкой.

## Канал и прайс-посты

Канал `@isellerhub`, id `-1003998743702`, бот в нём администратор.

**Модель:** пост публикуется ОДИН раз и дальше редактируется на том же
`message_id`. У каждого раздела стабильный `slug` — он связывает раздел каталога
с конкретным сообщением. Потерять slug = потерять сообщение и выложить дубль.

| файл | ответственность |
|---|---|
| `services/price_posts.py` | чистая генерация текста и клавиатур, без сети и БД |
| `services/price_channel.py` | состояние: что опубликовано, что изменилось |
| `services/info_posts.py` | редактируемые посты (гарантия, доставка) + конструктор кнопок |
| `services/telegram_publisher.py` | отправка/правка, retry, 429 |
| `services/telegram_bot.py` | обработчики команд, `build_reply` без сети |

Источник прайса — **каталог в БД**, не XLSX: пост обязан совпадать с тем, что
покупатель видит в Mini App. XLSX — только для импорта.

Каждый пост фиксируется в БД сразу после успеха. Если пачка упрётся в лимит
Telegram на середине, уже полученные `message_id` уцелеют и повторный прогон не
создаст дублей.

Инфо-посты с маркером `[уточнить]` система публиковать отказывается — забытый
черновик в канале хуже отсутствия поста.

## Навигация каталога — только из данных

**Списка категорий в коде больше нет.** Он был захардкожен в четырёх местах
(константа в `catalog.py`, сид `DEFAULT_CATEGORIES`, массивы во фронте, плюс
строки в прод-таблице `home_categories`), разъехался с базой — и плитки «Dyson»
и «Аксессуары» вели в пустой каталог. Тестов на `/catalog/categories` и `/home`
не было ни одного, поэтому баг дожил до прода.

Источник правды — сами товары, через `services/catalog_nav.py`:

| правило | где |
|---|---|
| категории = `SELECT DISTINCT category` по активным товарам | `list_categories()` |
| пустая категория не существует | там же, счётчик из товаров |
| плитка без товаров не выходит на главную | `has_products()` в `GET /home` |
| категория без плитки добавляется сама | слияние в `GET /home` |
| `is_active=False` у плитки — осознанное «скрыть», автодобавление её не воскрешает | там же |

Иконка и подпись — единственное, что нельзя вывести из данных: незнакомая
категория получает `FALLBACK_ICON` и подпись с заглавной буквы, но **в
навигацию попадает**. Добавлять её в код не нужно.

**Dyson — это бренд, а не категория.** Его 50 товаров лежат в `красота` и
`бытовая техника`; плитка с `action_type=category` физически не могла работать.
Для таких случаев есть `action_type=brand` → `/catalog?brand=Dyson`.

**Навигация двухосевая.** `GET /home` отдаёт `categories` и `brands`; бренды —
это `list_brands()` в `catalog_nav`, зеркало `list_categories()` поверх
`brand_counts()`. Раскладка: `action_type=brand` уходит на ось брендов, всё
остальное (включая непосчитаемые промо — поиск, подборка, AI) остаётся на оси
категорий. Правила видимости общие для обеих осей. На фронте — тумблер
«Категории / Бренды» над hero-чипами, состояние общее с desktop-сайдбаром,
иначе hero и сайдбар покажут разные оси. При пустом `brands` тумблера нет.

В прод-таблице `home_categories` остались две мёртвые строки — `id 6` (`dyson`
как категория) и `id 7` (`аксессуары`). Обе скрыты фильтром и пользователю не
видны; Dyson приходит на ось брендов автоматически из товаров. Удалить их можно
и стоит, но это косметика.

Фронт кэширует последний ответ `/catalog/categories` в localStorage
(`lib/categoryCache.ts`) — мгновенная отрисовка без сдвига вёрстки и без
выдуманных категорий. Устареть кэш может максимум на один визит.

**Грабли Docker на Windows:** Vite не видит правки через bind-mount (inotify не
работает), браузер продолжает крутить старый модуль даже после reload. Backend
с `uvicorn --reload` подхватывает нормально. Правил фронт — перезапусти
контейнер: `docker compose -f docker-compose.demo.yml restart frontend`.

## Порядок выдачи каталога

Правило живёт в ОДНОМ месте — `services/ranking.py`, и им пользуются каталог,
`/catalog/feed`, поиск и рекомендации:

```
in_stock -> popularity -> позиция категории из плиток -> цена -> id
```

**Зачем приор.** `popularity` обязана приходить из реального спроса или из
выгрузки магазина. Пока её нет, она нулевая у всех, и `ORDER BY popularity DESC`
вырождается: Postgres отдаёт строки в произвольном порядке, наверх выходит
импортированное первым. На проде так и было — в «Популярном» стояли AirPods
(id 31–45).

**Почему не список в коде.** Список «что важнее» разъедется с базой ровно так
же, как когда-то разъехался захардкоженный список категорий (см. выше). Поэтому
приор берётся из решения, которое УЖЕ принято и УЖЕ редактируется в админке —
порядка плиток главной (`home_categories.position`). Нужно поднять Dyson —
двигают плитку, а не правят код.

Что легко сломать обратно:

- **`id` в конце ключа обязателен.** Без него равные ключи снова дают
  произвольный порядок — ту самую проблему, которую чиним. Тест
  `test_order_is_fully_deterministic` держит это;
- **категория без плитки уходит вниз, но НЕ пропадает** (`NO_TILE_RANK`).
  Сейчас без плиток `часы`, `красота` и `бытовая техника` — они идут после
  консолей. Хотите задать им место осознанно — заведите плитки;
- **явные сортировки (цена, рейтинг, hot) тоже дополнены этим порядком.** Цена и
  рейтинг совпадают у десятков вариантов одной модели, без добора порядок внутри
  равных значений произволен;
- `__sale__` в приор не попадает: это виртуальная категория, у товара её в поле
  нет. Ось брендов — тоже, у неё свой разрез.

## AI-консультант и провайдеры

`AI_PROVIDER` выбирает транспорт, пайплайн у всех один:

```
extract_filters -> retrieve_candidates (только БД) -> ≤12 кандидатов -> модель
   -> строгая валидация JSON -> id обязаны быть подмножеством кандидатов
   -> денежные утверждения вырезаются -> карточки и цены ТОЛЬКО из to_card()
```

| значение | транспорт |
|---|---|
| `fallback` / `mock` | без LLM, ответ по каталогу (локальное демо по умолчанию) |
| `ollama_remote` | AI Gateway на Mac mini (`ai_remote.call_gateway`) |
| `anthropic` | Anthropic Messages API напрямую (`ai_anthropic.call_anthropic`) |
| `ai` | legacy AI Engine (`docker profile ai`, на проде не развёрнут) |

Оба LLM-транспорта возвращают `{content, model, total_ms}` и бросают
`AIGatewayError` — оркестратор не знает, кто отвечал, и при любой ошибке
деградирует в fallback. **Добавляя провайдер, соблюдай этот контракт**, иначе
придётся трогать проверенные защитные слои.

**Словарь категорий для AI тоже из данных.** `catalog_nav.category_vocabulary()`
собирает `{слово: категория}` из названий категорий и ПОДкатегорий, плюс тонкий
слой разговорных слов (`COLLOQUIAL`). Поэтому «фен» находит раздел: в БД есть
подкатегория «Фены» внутри категории `красота`. Два правила, которые легко
сломать обратно:

- **бренды из словаря выбрасываются** — иначе «Apple Watch» дал бы `apple` →
  `часы`, и любой запрос со словом apple уезжал бы в часы;
- **составные ключи сравниваются только точно** — по префиксу токен `apple`
  снова пролез бы в `apple watch`.

`_detect_category(text, vocab=None)` без словаря возвращает `None` и НЕ
подставляет ничего по умолчанию: молчаливая подстановка устаревшего списка и
была причиной ответов «нет в наличии» про товары с витрины. Промах категории
пишет warning в `techshop.ai.retrieval` и не убивает текстовую ветку.

**LLM не ищет по каталогу.** Модель видит максимум `AI_MAX_PRODUCT_CANDIDATES`
кандидатов, которые отобрал backend. Плохой retrieval = плохой ответ независимо
от модели: подключение LLM ничего не чинит в подборе.

### Anthropic — регион и гейтвей

**На проде работает Claude Haiku 4.5 через гейтвей на Vercel.** Прямой доступ
невозможен: `api.anthropic.com` отвечает `403 forbidden` с прод-VPS — это
региональное ограничение Anthropic, наступающее **до** проверки ключа (неверный
ключ даёт `401`), поэтому правильный ключ на проде ничего не менял. Проверено:

| откуда | ответ |
|---|---|
| прод напрямую | `403 forbidden` — "Request not allowed" |
| прод через WARP (`socks5://172.18.0.1:40000`) | `403 forbidden` — выходной узел в том же регионе |
| локальная машина | `401` — сеть и регион в порядке |
| Vercel (`iad1`) | работает |

Гейтвей — `gateway-vercel/`, проект Vercel `iseller-ai-gateway`, прозрачный
прокси `POST /v1/messages` (плюс `GET /api/health`). Он **намеренно ничего не
знает** про промпт, схему и модель: всё это остаётся в `ai_anthropic.py`, иначе
завелась бы вторая копия схемы, которая разъедется с валидатором.

Ключи: настоящий `ANTHROPIC_API_KEY` живёт **только в переменных Vercel**. На
VPS уезжает секрет гейтвея, он же лежит в `AI_ANTHROPIC_API_KEY` серверного
`.env`. Компрометация прода не даёт доступа к счёту Anthropic.

Прод-настройки: `AI_PROVIDER=anthropic`,
`AI_ANTHROPIC_BASE_URL=https://iseller-ai-gateway.vercel.app/api`. SDK сам
дописывает `/v1/messages`. `count_tokens` через прокси **не проходит** — он
проксирует только `/v1/messages`.

**Кэширование промпта на Haiku не включается.** Минимальный кэшируемый префикс
на Haiku 4.5 — 4096 токенов, а кэшировать можно только `tools`→`system`→
`messages` (схема лежит в `output_config` и в префикс не входит). Наш системный
промпт — 3909 символов, около 1500–1900 токенов, меньше половины порога.
`cache_control` там не даст ошибки, просто вернёт нулевой
`cache_creation_input_tokens`. Не трать на это время.

**Экономия, которая работает:** `AI_MAX_PRODUCT_CANDIDATES=8` (было 12; кандидаты
— основная статья входных токенов) и `AI_SKIP_LLM_FOR_BROWSE=true` — простой
просмотр каталога («айфон», «dyson») отвечается из БД без вызова модели, за
26–143 мс вместо 8 секунд. Условие узкое, см. `_is_plain_browse` в
`ai_orchestrator.py`: начало диалога, до 3 слов, нет слов-маркеров совета,
попадание в категорию или бренд. Совет, сравнение и задача идут в модель.
Один запрос к модели стоит примерно 0.4 цента.

Модель по умолчанию — `claude-haiku-4-5`. На Haiku 4.5 **не поддерживаются**
`effort` и adaptive thinking — не добавляй их, будет 400.

Ответ просим через structured outputs (JSON Schema). Схема собрана из тех же
`INTENTS`/`NEXT_ACTIONS`, что валидирует `ai_schemas`, — разъехаться не могут.
Если API схему не принял, клиент **один раз повторяет запрос без неё**: промпт и
так требует строгий JSON, а парсер умеет repair. Молчаливая деградация на каждом
запросе — самый дорогой вид отказа, поэтому она недопустима.

Живая проверка (ключ только из окружения, в вывод не попадает):

```bash
cd backend && AI_ANTHROPIC_API_KEY=... python -m app.scripts.smoke_anthropic
```

## Корзина и общая заявка

Корзина — список выбранной техники, который уходит менеджеру ОДНОЙ заявкой.
Не оплата, не бронь, склад не трогается: `products.stock` — это склад, а не
резерв.

| файл | ответственность |
|---|---|
| `services/availability.py` | режим доступности товара — ЕДИНСТВЕННЫЙ резолвер |
| `services/cart.py` | владение, количества, цены, checkout-транзакция |
| `api/cart.py` | тонкий HTTP-слой над правилами |
| `frontend/lib/cartMath.ts` | чистая арифметика и правила (тесты в node) |
| `frontend/lib/cart.ts` | серверное состояние + оптимистичный UI |

**Заявка-корзина — это тот же `Lead`**, а не отдельная сущность: на `Lead` висят
`/leads/my`, экран «Заявки», список админки, фильтры, дашборд и аналитика
источников. Отдельная таблица потребовала бы продублировать шесть интеграций
вручную — а это прямой путь к «пользователь получил success, менеджер заявки не
видит». Позиции — в `lead_items` со снапшотами; `lead_type='cart'`,
`source='telegram_mini_app_cart'`.

`product_id` у `lead_items` — **ON DELETE SET NULL**, у `cart_items` — CASCADE.
Разница осознанная: удаление товара не имеет права утащить позиции уже
отправленной заявки, но из живой корзины исчезнувший товар убрать обязано.

`added_price` — снапшот на момент добавления, НЕ актуальная цена. Сумма всегда
считается по `products.price`; расхождение показывается как «Цена обновилась».

**`products.availability_mode` — nullable, NULL = вывод из `in_stock`/`is_limited`.**
Это и есть гарантия, что миграция не изменила поведение 217 существующих товаров.
Явное значение нужно только для `out_of_stock` и `preorder` — флагами их не
сказать.

`idempotency_key` уникален **в пределах пользователя**. Глобально уникальный ключ
позволял бы чужому клиенту занять значение и сломать checkout соседу.

**Оптимистичное обновление применяется СИНХРОННО, в очередь уходит только
сетевой запрос.** Если положить обновление состояния внутрь очереди, второе
быстрое нажатие «+» будет ждать ответа на первое — и смысл оптимистичности
пропадает. Очередь нужна для порядка записей на сервере, а не для UI.

Панель корзины скрыта на `/cart` (был бы дубль) и на карточке товара (встала бы
поверх её фиксированной CTA). Safe-area компенсируется один раз — переменной
`--bottom-nav-height`, общей с `.cta-dock`.

## Баллы и уровни (v5.8.0)

Покупатель копит кэшбек с покупок, ставка растёт с оборотом: 0,25% → 2%.
Спека — `docs/superpowers/specs/2026-08-01-loyalty-design.md`.

| файл | ответственность |
|---|---|
| `models/loyalty.py` | журнал `loyalty_transactions` — единственный источник правды |
| `services/loyalty.py` | лестница `LEVELS`, агрегаты, `record()` со всеми проверками |
| `api/loyalty.py` | `GET /loyalty/me` — счёт покупателя |
| `api/admin_users.py` | раздел «Клиенты»: список, карточка, операции |
| `frontend/lib/loyalty.ts` | типы и чистая арифметика (тесты в node) |

**Баланса на `users` НЕТ и заводить его нельзя.** `balance = SUM(points)`,
`lifetime_spent = SUM(amount) WHERE kind='purchase'`. Денормализованная копия
агрегата разъедется с журналом молча — тот же класс ошибки, что захардкоженный
список категорий против базы. При сотнях пользователей это один `GROUP BY` по
индексу (`loyalty.totals` считает страницу целиком, не строку за строкой).

**Начисление только вручную из админки.** Автоматики на статусе заявки нет
намеренно: заявка — не покупка. `estimated_total` оценочный, сделка срывается,
состав меняется, фиксации оплаты в магазине нет вовсе. Автоначисление раздало бы
баллы за то, чего не было; оно стоит в роудмапе и появится вместе с оплатой.

Правила, которые легко сломать обратно:

- **уровень растёт на обороте, а списание оборот не уменьшает.** Потратил баллы
  — уровень не упал. Пороги в рублях понятны человеку; пороги в баллах зависели
  бы от ставки, то есть сами от себя;
- **`rate_bps` — снапшот на момент операции**, как `added_price` у корзины: через
  полгода нужно знать, по какой ставке начислили, а не по какой начислили бы
  сегодня;
- **округление баллов ВНИЗ.** Вверх дарило бы по баллу на каждой операции;
- **баланс не уходит в минус** — проверку держит `record()`, а не спрятанная
  кнопка в UI;
- **ручки «поставить баланс = N» нет.** Баланс — следствие журнала; обнуление
  проводится корректировкой с обязательным комментарием;
- `idempotency_key` уникален **в пределах пользователя** (тот же приём, что у
  `leads`): двойной клик по «Начислить» не даёт двойной кэшбек;
- **лестница живёт только в `services/loyalty.py`.** Фронт и админка получают её
  из API. Вторая копия порогов означала бы, что покупателю показывают не тот
  уровень, по которому ему начисляют.

Экран `/loyalty` в Mini App: счёт, прогресс до следующего уровня, лестница,
история и роудмап программы (`components/LoyaltyRoadmapSheet.tsx`, шелл
`SheetShell` общий с роудмапом AI). **Сроков в роудмапе нет** — по тому же
правилу, что и в AI: дата это обещание, а обеспечить его некому.

## Уведомления пользователю (патч 1.1)

Всё, что магазин говорит покупателю в Telegram, идёт через **outbox** — таблицу
`notifications`. План патча целиком — `PATCH_1.1.md`.

| файл | ответственность |
|---|---|
| `models/notification.py` | очередь: `dedupe_key` UNIQUE, статусы, попытки |
| `services/notification_templates.py` | тексты и клавиатуры, чистые функции |
| `services/notifications.py` | `enqueue()` (producer) и `drain()` (consumer) |
| `services/cart_reminders.py` | скан брошенных корзин |
| `services/favorite_watch.py` | скан избранного: подешевело / снова в наличии |

**Producer не ходит в сеть.** `enqueue()` пишет строку ТОЙ ЖЕ транзакцией, что
и событие (смена `Lead.status` в `admin_crm.update_lead`). Отправлять из
HTTP-запроса нельзя: Telegram за WARP стоит секунды и падает, а менеджер не
должен ждать его, чтобы сменить статус, — и тем более смена статуса не должна
падать вместе с Telegram.

**Consumer — сервис `bot`**, функция `_tick` в `scripts/bot_polling.py`. Своего
планировщика (cron/celery/APScheduler) в проекте НЕТ и заводить не нужно: этот
процесс уже крутится с шагом ≤30 с. Новый постоянный процесс = новая точка
отказа и новый повод поймать 409 Conflict вторым экземпляром бота.

Правила, которые легко сломать обратно:

- **`dedupe_key` — единственная защита от дублей**, и держит её БД, а не
  проверка «сначала посмотрим». Дубль ловится откатом до SAVEPOINT, поэтому
  внешняя транзакция (сама смена статуса) уцелевает;
- ключ корзины — `cart:{id}:{updated_at}`: одно напоминание на одно СОСТОЯНИЕ
  корзины. Отдельного поля «когда напоминали» не нужно;
- **доставка at-least-once**: `sent` ставится ПОСЛЕ отправки. Обратный порядок
  дал бы тихую потерю уведомления, что хуже одного дубля;
- постоянные ошибки (`bot was blocked`, `chat not found`) уводят строку в
  `failed` сразу — попытки на них не тратятся;
- **в `_send` нет fallback'а на канал.** `publisher.send_message` подменяет
  пустой адресат на `TELEGRAM_CHANNEL_ID` — для постов канала удобно, здесь
  катастрофа: состав и сумма заявки ушли бы в открытый канал;
- без `TELEGRAM_BOT_TOKEN` очередь **не наполняется вовсе**. Иначе первый запуск
  с токеном вывалил бы на людей всю накопленную историю статусов.

Тихие часы напоминаний — 22:00–10:00 МСК (`CART_REMINDER_QUIET_*`). МСК не
переводит часы с 2014-го, поэтому сдвиг фиксированный, без базы часовых поясов.

### Избранное: точка отсчёта — в самой строке

`product_favorites.notified_price` и `notified_in_stock` — это «что про этот
товар пользователь от нас уже слышал». Без них «цена снизилась» бессмысленно:
снизилась относительно ЧЕГО. Сравнивать с прошлым сканом нельзя — тогда после
каждого прогона цена «свежая».

- **NULL = мы ещё ничего не сообщали.** Первый скан такие строки ЗАПОЛНЯЕТ и
  молчит. Иначе выкладка патча стала бы рассылкой по всему избранному разом;
- отметка ставится **сразу при добавлении** (`_baseline` в `api/favorites.py`,
  включая `/merge`), а не первым сканом — иначе снижение между добавлением и
  сканом пропало бы;
- **`notified_price` только убывает.** При росте цены не поднимается, поэтому
  колебание 100→90→100→90 даёт одно сообщение, а не три;
- **`notified_in_stock` пишется ВСЕГДА**, даже когда сообщение не отправляется:
  товар, ушедший со склада, обязан вернуть отметку в False, иначе следующее
  поступление не будет распознано как новость;
- «Снова в наличии» — только про `in_stock`/`limited`. `on_request` и `preorder`
  тоже orderable, но назвать их наличием значит позвать за тем, чего нет.

**В `_candidates` нет SQL-фильтра «кому есть что сказать» — и это осознанно.**
Такой фильтр там был и отсекал товар, только что ушедший со склада: цена не
менялась, отметка ещё True, строка в выборку не попадала, флаг не сбрасывался.
Наличие выводится в Python из четырёх флагов плюс явной колонки, и любое его
повторение в SQL — вторая версия правила, которая разъедется с первой.

## Поделиться товаром и ярлык на домашнем экране (патч 1.1)

**Делиться внутренним адресом Mini App нельзя.** Кнопка «Поделиться» слала
`window.location.href` — получатель открывал его в обычном браузере, где нет
Telegram-авторизации, и видел «Не удалось войти». Ссылка от друга вела в тупик,
а выглядело это как сломанный магазин.

Теперь делимся deep link'ом `t.me/<bot>?start=product_<id>` — тот же приём, что
у кнопок канала и по той же причине. Логика выбора — `frontend/lib/share.ts`
(чистая, тестируется в node), разбор payload — `parse_product_payload` в
`services/telegram_bot.py`.

- `bot_username` отдаётся через `GET /api/config/public`. Не секрет: он и так
  стоит в каждой кнопке каждого поста канала;
- `parse_product_payload` проверяет ASCII-цифры, а не `isdigit()`: последний
  принимает юникод-цифры («٤٢»), а результат уходит в URL кнопки;
- `reply_for_payload` **не читает название товара из БД** — `build_reply` и
  `reply_for_payload` не ходят ни в сеть, ни в базу, и всё поведение бота
  проверяется обычными тестами. Название человек видит в сообщении, по которому
  пришёл.

**Ярлык на домашний экран** (`addToHomeScreen`, Bot API 8.0) — блок в профиле,
видимый ТОЛЬКО при статусе `missed`. Вне поддерживающего клиента SDK бросает
`WebAppMethodUnsupported` синхронно (колбэк не вызывается вовсе), поэтому в
`checkHomeScreenStatus` есть и `try/catch`, и таймаут: клиент может метод
объявить, но не ответить, и тогда Promise повис бы навсегда вместе с кнопкой.
Любая неопределённость = `unsupported`: кнопка, которая ничего не делает, хуже
её отсутствия.

## Социальное доказательство (патч 1.1)

Одна строка на карточке — «Заказывали 5 раз за месяц» или «В избранном у 7
человек». Считает `services/social_proof.py`, показывают карточка товара и
плитка каталога (`apply_social_proof` — тот же приём, что `apply_group_images`:
два запроса на весь ответ, а не по паре на карточку).

**Источник — таблицы фактов, а не события.** В `user_product_events` уже лежат
`favorite_add` и `lead_created` с индексом по товару, но `POST
/api/events/product` принимает эти типы ОТ КЛИЕНТА. Для персональных
рекомендаций безопасно (человек портит свою выдачу), для числа, которое видят
все, — нет: любой клиент нарисовал бы любому товару любую популярность.
Поэтому считаем по `lead_items` + `leads` и `product_favorites`.

- заказы считаются по ОБОИМ видам заявок: у корзины товары в `lead_items`, у
  одиночной — в `leads.product_id`. Только первый вид = потерять почти весь
  спрос (на проде было 3 заявки и 0 позиций корзины);
- считаем ЗАЯВКИ, а не позиции: пять штук в одной корзине — один заказ;
- отменённые заявки исключены, окно — 30 дней;
- избранное защищено уникальным индексом `(user_id, product_id)`: один человек
  = один голос;
- ниже порога (`3` заказа / `5` избранных) бейджа нет вовсе;
- бейдж ОДИН: заказы важнее избранного. Три бейджа подряд читаются как реклама.

Текст «В избранном у N человек» выбран не по вкусу: вариант «N человек добавили
в избранное» шире плитки каталога (169–180px против 149px) и обрезался бы
многоточием. Второй, короткий текст для плитки заводить нельзя — это две версии
одного утверждения.

**Грабли демо-стенда:** `docker-compose.demo.yml` монтирует только
`frontend/src`. `tailwind.config.js`, `package.json` и прочее остаются из
образа, поэтому правки в них не подхватываются ни перезапуском, ни очисткой
кэша Vite — нужен `docker compose -f docker-compose.demo.yml up -d --build
frontend`. Симптом: локально `text-muted` рисуется чёрным (старый конфиг с
`var(--app-sub)` вместо `rgb(var(--app-sub) / <alpha-value>)`), в проде — серым.

## Powered by Claude и роудмап AI (патч 1.2)

Бейдж на экране `/ai` со знаком Claude; по нажатию — шит с роудмапом из семи
шагов (`components/AiRoadmapSheet.tsx`).

**Бейдж показывается только когда движок РЕАЛЬНО Claude.** `GET
/api/config/public` отдаёт `ai_vendor` (`"claude"` при `AI_PROVIDER=anthropic`,
иначе пусто) и `ai_model`. Фронт не имеет права утверждать это от себя:
`ollama_remote` — это Ollama на Mac mini, `fallback` — ответ из каталога вообще
без модели, и бейдж там был бы враньём про собственный магазин. Недоступный
конфиг = пустой vendor = молчание, а не утверждение по умолчанию.

Знак Claude — `components/ClaudeMark.tsx`, одиннадцать лучей по кругу,
`CLAUDE_ORANGE = #D97757` одной константой на знак и акценты шита. Формулировки
намеренно означают атрибуцию, а не партнёрство: в шите прямо сказано, что
роудмап — планы магазина, а не Anthropic. Сроков в роудмапе нет: дата — это
обещание, а обеспечить его некому.

`SheetShell` из `ScenarioSheet.tsx` теперь экспортируется — второй шелл означал
бы вторую ловушку фокуса и блокировку скролла, которые расходятся молча.

**Списки событий аналитики фронта и бэкенда обязаны совпадать.** Они уже
расходились дважды: фронт объявлял событие в `AppEvent`, backend не находил его
в `ALLOWED_EVENTS` и отвечал 400, а `track()` — fire-and-forget с проглоченной
ошибкой. Итог: события молча не доходили, и в отчёте «кнопкой не пользуются»
вместо «кнопку не посчитали». Так терялись пять событий (`home_axis_switched`,
`search_mode_switched`, `product_shared`, `home_screen_prompted`,
`ai_roadmap_opened`). Расхождение теперь ловит `test_event_allowlist_sync.py` —
он читает union `AppEvent` прямо из `analytics.ts`.

## Что помнить про секреты

Токен бота лежит в пути URL Bot API (`/bot<TOKEN>/sendMessage`), поэтому
`httpx`/`httpcore` приглушены до WARNING — иначе токен пишется в `docker logs` на
каждое сообщение. Не поднимай им уровень обратно.
