# Ревизия админки — 2026-08-04

Что в админке реально работает, что мертво и почему. Составлено перед решением
переносить панель управления в Dexo.

Метки достоверности:

- **[замер]** — воспроизведено в запущенной админке (localhost:5174, dev-вход),
  подтверждено сетевым запросом, геометрией DOM или состоянием хранилища;
- **[код]** — следует из чтения исходников, в живом UI отдельно не проверялось.

Стенд: `docker-compose.demo.yml`, backend 8000, admin 5174. Данные — локальная БД
со снимком каталога (46 iPhone, 34 Dyson и т.д.).

## 1. Из чего админка состоит

`admin/` — отдельное Vite+React приложение, 3997 строк в 10 файлах, **без
роутера, без стейт-менеджера, без CSS-фреймворка и без единого теста**. Стили —
инлайновые объекты из `admin/src/ui.ts`. Зависимости: только `react` и
`react-dom`.

| файл | строк | экран |
|---|---|---|
| `App.tsx` | 665 | вход, шапка с 12 вкладками, Дашборд, Заявки |
| `HomeAdmin.tsx` | 889 | Импорт, Главная (баннеры/категории), Медиа |
| `Products.tsx` | 842 | Товары |
| `PricePosts.tsx` | 431 | Прайс канала |
| `Customers.tsx` | 386 | Клиенты |
| `ChannelPosts.tsx` | 352 | Посты канала |
| `Posts.tsx` | 111 | Посты (редакционные) |
| `Analytics.tsx` | 118 | Аналитика, AI-логи |
| `ui.ts` | 194 | стили + api-хелперы |

Навигация — `useState<Tab>`. Следствий три: адреса у разделов нет (нельзя дать
ссылку на экран), кнопка «назад» в браузере выходит из админки, F5 сбрасывает всё.

## 2. Как админка связана с ботом и витриной

Прямой связи админки с ботом нет — только через backend. Это хорошая новость для
замены интерфейса: Mini App и бот не заметят, если панель станет другой.

```
админка ──HTTP──> FastAPI ──> PostgreSQL
                     │            ├── каталог ──> Mini App
                     │            ├── заявки
                     │            └── настройки главной ──> Mini App
                     ├──> notifications (очередь) ──> сервис bot ──> клиент в Telegram
                     └──> telegram_publisher ──> Bot API ──> канал
```

Два канала связи с Telegram устроены по-разному:

- **уведомления клиентам** идут через очередь: админка меняет статус заявки →
  запись в `notifications` → отдельный сервис `bot` разбирает. Telegram упал —
  изменение заявки не потеряно. Сделано правильно;
- **публикации в канал** идут синхронно: админка → backend →
  `telegram_publisher.call()` → Bot API. Ошибка Telegram приходит наверх как 502.

## 3. Подтверждённые дефекты

### 3.1 Экран «Посты канала» не может показать ни одного поста **[замер]**

Самый дорогой дефект: раздел неработоспособен полностью, при этом всё под ним
исправно.

Воспроизведение: вкладка «Посты канала» → «Добавить типовые».

```
POST /api/admin/price-posts/info/generate  → 200
     {"created":["info_warranty","info_delivery","info_payment",
                 "info_preorder","info_about"]}
GET  /api/admin/price-posts                → 200
     posts: 10 записей, у всех kind:"price", editable:false
Экран: «Постов пока нет.»
```

Причина — разрыв между записью и чтением:

- `backend/app/api/price_posts.py:78` — список фильтрует
  `kind IN (PRICE_KIND, NAVIGATION_KIND)`; записи `kind="info"` не попадают в
  выдачу **никогда**;
- `backend/app/api/price_posts.py:71` — `editable = (kind == INFO_KIND)`;
- `admin/src/ChannelPosts.tsx:60` — экран оставляет из ответа только
  `p.editable`, то есть ровно те записи, которых в ответе не бывает.

Эндпоинта, который отдаёт список инфо-постов, в backend нет вообще (проверено
grep по `INFO_KIND`). Созданные посты живут в БД, редактируются через
`PATCH /info/{slug}` и публикуются через `/info/publish` — но увидеть их из
админки нельзя.

### 3.2 Главное действие экрана «Заявки» физически за краем окна **[замер]**

Таблица заявок — 12 колонок. При ширине окна 1024:

```
ширина таблицы 1322px, контейнер 959px  → скрыто 363px (28%)
кнопка «Открыть»: left=1263, right=1335 при innerWidth=1024
```

Кнопка «Открыть» — последняя колонка, то есть единственный способ открыть заявку
уезжает за правый край первым. Чтобы нажать, нужно проскроллить таблицу вбок.
Это и есть «кнопки не нажимаются»: кнопка есть, она рабочая, но её не видно и
непонятно, что до неё надо доехать.

### 3.3 Шапка съедает 14% экрана и переносится на две строки **[замер]**

12 вкладок в один ряд `flexWrap: "wrap"`:

| ширина окна | высота шапки | рядов вкладок |
|---|---|---|
| 1280 | 101px | 2 |
| 1024 | 101px (14% высоты) | 2 |

При этом `main` ограничен `maxWidth: 1150` — на широком мониторе контент сжат в
узкую колонку, а таблицы всё равно скроллятся вбок. Ширина экрана используется
плохо в обе стороны.

### 3.4 Сессия живёт 30 минут и умирает молча **[замер]**

- `localStorage`, `sessionStorage`, `cookie` — **пустые**; токен лежит только в
  `useState` (`App.tsx:16`). Любой F5 — разлогин;
- backend отдаёт пару токенов (`auth.py:44`), админка берёт из ответа только
  `access_token` (`App.tsx:54, 65`) и **выбрасывает refresh**;
- `ACCESS_TOKEN_MINUTES = 30` (`core/config.py:47`);
- по всей `admin/src` нет ни одного упоминания `refresh_token`, `auth/refresh`
  или обработки `401` (проверено grep — 0 совпадений).

Через полчаса работы каждый запрос отдаёт 401. Админка при этом выглядит рабочей:
из логина не выкидывает, а результат нажатия зависит от экрана — где-то красная
строка `HTTP 401`, где-то ничего. Это второй источник жалобы «кнопки не
нажимаются».

### 3.5 Подпись к фото режется молча **[код]**

`services/telegram_publisher.py:189` — `"caption": text[:1024]`.

Пост с картинкой в Telegram ограничен 1024 символами, без картинки — 4096.
Админка разрешает 4096 в обоих случаях (`api/posts.py:19`,
`Field(max_length=4096)`), поля счётчика для режима с картинкой нет,
предупреждения нет. Написали длинный пост, приложили картинку, нажали
«Опубликовать» — в канал ушёл обрезанный текст, и админка отрапортовала успех.

### 3.6 Редакционный пост нельзя создать из интерфейса **[замер+код]**

`POST /admin/posts` в backend есть (`api/posts.py:67`), в `admin/src` вызова
нет — grep по `apiPost("/admin/posts"` пуст. Экран «Посты» умеет только
разбирать то, что кто-то создал помимо админки, а генератора черновиков нет —
отсюда вечная заглушка «Черновиков пока нет».

### 3.7 Опубликованный редакционный пост не редактируется — по устройству **[код]**

`api/posts.py:79` — `if post.status == "published": raise HTTPException(409)`.
Команды «изменить опубликованное сообщение» для этих постов нет, хотя
`telegram_publisher.edit_message()` существует и им пользуются прайс- и
инфо-посты. То есть механика правки на месте есть, к редакционным постам она
просто не подключена.

### 3.8 Три несовместимые модели постов под одним словом «пост»

Пользователь видит три вкладки и не понимает, чем они отличаются:

| | «Посты» | «Прайс канала» | «Посты канала» |
|---|---|---|---|
| текст пишет | AI/человек | генератор из каталога | человек |
| статусы | draft/approved/published/rejected | draft/published/outdated/error | те же, что у прайса |
| правка после публикации | запрещена (409) | обновляет тот же message_id | обновляет тот же message_id |
| кнопки | нет | есть | есть |
| экран работает | частично | да | **нет** (см. 3.1) |

Три модели статусов, три модели правки, одно слово. Любой новый человек в этой
панели ошибётся.

## 4. Коннекторы: что подключено, а что нет

### 4.1 Баннеры главной — CRUD жив, но внешний вид ему не подчиняется **[замер]**

Это ответ на «баннеры я не могу менять». Цепочка `админка → БД → GET /home →
Home.tsx` **исправна**: список читается, правка сохраняется, загрузка картинки
отрабатывает (`POST /admin/uploads/image → 201`, файл сразу отдаётся с
`/api/uploads/...`), поля формы заполняются существующими значениями.

Не работает другое — **картинка баннера живёт не в админке, а в коде витрины**:

```
GET /api/admin/home/banners
#0 id=6  GTA VI + PlayStation 5 Pro 2 ТБ  img=/assets/promos/gta6-ps5-pro-bundle-v4.webp
#1 id=1  iPhone в наличии                 img=None
#2 id=2  MacBook для работы               img=None
#3 id=3  PlayStation сегодня              img=None
#4 id=4  Подберём лучшую цену             img=None
#5 id=5  Техника с гарантией              img=None
```

Единственный баннер с картинкой ссылается на файл, **положенный руками в
`frontend/public/assets/promos/`** (в git он до сих пор untracked), а не на
`/api/uploads/...` из загрузчика админки. У остальных пяти `image_url = None`, и
их вид определяет функция `curatedPromo()` в `frontend/src/pages/Home.tsx:66` —
она подбирает картинку **по ключевым словам в заголовке**:

```
заголовок содержит "iphone"       → /assets/promos/iphone-studio.webp
                   "macbook"      → /assets/promos/macbook-studio.webp
                   "playstation"  → /assets/promos/playstation-studio.webp
                   "гарант"       → /assets/promos/warranty-studio.webp
                   "лучш"         → /assets/promos/claude-price-studio.webp
```

Практические следствия, и все три бьют по одному месту:

1. переименовал баннер в админке — потерял картинку, потому что заголовок
   перестал совпадать с ключевым словом. Правка текста незаметно меняет
   оформление;
2. новый баннер с новой картинкой требует **деплоя фронта**, если хочется того
   же качества, что у существующих: через админку можно только загрузить файл
   без кадрирования, позиционирования и контроля читаемости текста поверх;
3. управление фоном в админке — это текстовое поле, куда надо руками написать
   `linear-gradient(135deg,#1a7fd4,#6d5ae0)`. Ни палитры, ни пипетки.

То есть админка управляет **текстом и действием** баннера, а его **видом**
управляет код витрины. Разделение проходит ровно по границе, которая
пользователю не видна.

### 4.2 Кнопки категорий — единственная часть главной, которая слушается полностью

`action_type` + `action_value` из админки напрямую определяют переход. Правило
видимости в `GET /home` (плитка без товаров не показывается, категория без
плитки добавляется сама) описано в CLAUDE.md и работает.

### 4.3 Мёртвые связи

Эндпоинты, которые backend отдаёт, а админка не вызывает (проверено grep):

| эндпоинт | что теряем |
|---|---|
| `GET /admin/audit` | журнал действий пишется, но посмотреть его из UI нельзя |
| `GET /admin/stats` | — |
| `GET /admin/loyalty/levels` | уровни лояльности только зашиты в `Customers.tsx` |
| `PATCH /admin/products/{id}/stock` | отдельная правка остатка |
| `POST /admin/import/products/preview\|confirm` | старый одиночный импорт |
| `POST /admin/import/image-groups/preview\|confirm` | групповое сопоставление фото |
| `POST /admin/posts` | создание редакционного поста (см. 3.6) |

Обратный случай — код в админке, до которого нельзя дойти:
`Products.tsx:782` экспортирует `ImportTab` (~60 строк), его не импортирует
никто. Старый экран импорта, оставшийся в бандле.

### 4.4 Обработка ошибок

- 65 вызовов `api*` на 45 `catch` по всей `admin/src`;
- два «глухих» перехвата: `ChannelPosts.tsx:67` и `Products.tsx:430` —
  `.catch(() => {})`;
- первый из них опасен: если `GET /info/button-kinds` не ответит, `kinds`
  останется `null`, а обе модалки отрисованы как `{editing && kinds && ...}` и
  `{creating && kinds && ...}` — кнопки «Новый пост» и «Редактировать» станут
  нажиматься **без всякой реакции и без сообщения**;
- `uploadImage` в `HomeAdmin.tsx:488` не обёрнут ничем: ошибка загрузки
  (не тот формат, слишком большой файл, истёкший токен) не покажет ничего;
- ни один экран не блокирует кнопку на время запроса — двойное нажатие
  «Опубликовать» уходит в Telegram дважды.

### 4.5 Тестов интерфейса нет вовсе

В `admin/` не установлен даже vitest; `admin/src/*.test.*` не существует.
`npm run build` — это `tsc -b && vite build`, то есть проверяется только
типизация. Поэтому дефект 3.1 и прошёл: бэкенд-тест доказал, что инфо-пост
создаётся через API, а что он появится на экране — не проверял никто.

## 5. Что стоит сохранить

Ядро под интерфейсом здоровое, переписывать его не нужно:

- каталог и товары в PostgreSQL, Mini App читает реальные данные;
- заявки со снапшотом состава и сравнением с актуальным каталогом
  (`App.tsx:435` — снапшот намеренно не редактируется, это правильно);
- очередь уведомлений, отделённая от Telegram;
- Import Center: preview → confirm с job_id, диффом, отчётом по файлам,
  выгрузкой ошибок в CSV, идемпотентным повтором. Лучшая часть админки;
- массовая загрузка фото по SKU и аудит покрытия фото;
- прайс-посты: генерация из каталога, `message_id`, правка того же сообщения,
  `plan`/`preview`/`dry_run` перед отправкой. Эталон того, как надо;
- инлайновая правка цены и остатка + массовые действия в «Товарах»;
- `AuditLog` пишется на все опасные действия.

## 6. Вывод

Дефекты делятся на два разных класса, и лечатся они по-разному.

**Класс А — обрывы связи** (3.1, 3.4, 3.5, 3.6, 4.3, 4.4). Это не вопрос
дизайна, это несведённые концы. Чинится точечно, в существующем коде, за часы:
эндпоинт списка инфо-постов, хранение и обновление токена, лимит подписи,
кнопка создания поста, показ ошибок.

**Класс Б — устройство интерфейса** (3.2, 3.3, 3.7, 3.8, 4.1). Это следствие
того, что панель писалась как технический доступ к API, а не как рабочее место:
12 равноправных вкладок вместо задач, таблица на 12 колонок вместо главного и
второстепенного, три модели постов вместо одной, вид витрины в коде вместо
управляемого содержимого. Точечными правками не лечится — это переделка.

Отсюда разумное разделение: класс А закрыть в текущей админке (иначе магазином
нельзя работать прямо сейчас), класс Б не чинить, а забрать в Dexo — там он
решается один раз и правильно.
