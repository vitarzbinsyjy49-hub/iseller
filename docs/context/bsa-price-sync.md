# Сверка цен с BSA (Big Sale Apple) — еженедельная задача

> Читать, когда пользователь присылает новую выгрузку конкурента (`result.json`
> из экспорта Telegram Desktop) и просит свериться/обновить цены. Инвариант в
> `CLAUDE.md`.

## Кто это и зачем

**BSA («Big Sale Apple»)** — чужой канал (поставщик/конкурент), НЕ наш. Реальная
розница в Москве (Багратионовский проезд 7к3, ТЦ Горбушкин двор — тот же
Горбушкин двор, что в самовывозе нашего магазина). Пользователь раз в
~неделю выгружает историю этого канала через Telegram Desktop («Экспорт
истории чата» → JSON) и присылает `result.json`.

**Правило цены (озвучено владельцем впрямую):** наша цена = цена BSA минус
300–500 ₽. Уже закодировано как `NAKIDKA = 500` в
`backend/app/scripts/import_bsa.py:37` — взята нижняя граница диапазона одним
числом, «чтобы правило было проверяемым, а не „примерно“». Если владелец
попросит другое число — там и менять, один константа.

## Шаги на новую выгрузку

1. **Взять `result.json`** — путь пользователь пришлёт (например
   `C:\Users\<user>\Downloads\Telegram Desktop\ChatExport_YYYY-MM-DD\result.json`).
   Это полная история канала (сотни сообщений: iPhone, Mac, но и JBL-колонки,
   GoPro, Samsung, Яндекс-станции — не наш ассортимент, пропускать).

2. **Достать читаемый текст сообщений.** Структура экспорта: `messages[]`,
   `type=="message"`, поле `text` — либо строка, либо список chunks (строка
   или `{"type":..., "text":...}`) — конкатенировать.

   **Одного `text` НЕ ХВАТАЕТ.** Форматированные посты Telegram Desktop
   отдаёт деревом `rich_message` (`blocks[] -> paragraph -> concat -> bold /
   text_link / plain`), а `text` у них ПУСТАЯ строка. В выгрузке от
   02.09.2026 именно так пришли оба поста с iPhone (id 12966 — 17/17e/Air,
   id 12968 — 17 Pro/Pro Max): плоский разбор показывал «сообщение без
   текста», и весь блок iPhone молча пропадал — а это основная часть
   прайса. Разбирать надо ОБА поля: `text` или, если он пуст,
   рекурсивный обход `rich_message`. Пример разбора (Python):
   ```python
   import json
   data = json.load(open(path, encoding="utf-8"))
   def flatten(t):
       if isinstance(t, str): return t
       return "".join(c if isinstance(c, str) else c.get("text","") for c in t)
   def rich(node):
       if isinstance(node, str): return node
       if isinstance(node, list): return "".join(rich(x) for x in node)
       if isinstance(node, dict):
           if node.get("type") == "paragraph": return rich(node.get("text")) + "\n"
           if "blocks" in node: return "".join(rich(b) for b in node["blocks"])
           if "text" in node: return rich(node["text"])
       return ""
   for m in data["messages"]:
       if m.get("type") == "message":
           txt = flatten(m.get("text", "")) or rich(m.get("rich_message"))
   ```
   (Уже сделано один раз для выгрузки от 18.08.2026 — сырой вывод лежит в
   `C:\Users\pipij\AppData\Local\Temp\claude\C--iseller-demo\0b1b3e94-7774-4138-ada7-6353b3b80dff\scratchpad\bigsale_texts.txt`,
   но это чужая scratchpad-папка другой сессии — может быть уже удалена,
   не полагаться на неё, разобрать заново из `result.json`, если файла нет.)

3. **Найти актуальные блоки iPhone 17 и Mac/мониторы/аксессуары**, привести к
   формату, который понимает парсер — см. `data/bsa_2026_08_11.txt` и
   `data/bsa_mac_2026_08_11.txt` как эталон. Ключевые правила формата (полный
   разбор — в самом `bsa_parser.py`, он не угадывает и молча не пропускает:
   нераспознанная строка с ценой попадает в `failed`):
   - iPhone: `<модель> <память> <цвет>-<цена><флаги региона>(<sim-пометка>)`,
     например `17 Pro 256 Silver-99.800🇭🇰🇰🇷(1sim+e sim)`. Модель — **только
     17 / 17 Pro / 17 Pro Max / 17e** (`_MODEL_RE` в `bsa_parser.py:48`), другие
     поколения (15/16, SE и т.д.) парсер не берёт — если понадобятся, это
     отдельная доработка регулярки, не часть обычного еженедельного прогона.
   - Mac/мониторы/аксессуары: артикул в `[СКОБКАХ]` или после `|`, если есть —
     он совпадает с нашим SKU в каталоге (см. пример `[MCX44]` в выгрузке
     18.08.2026 — то же самое, что наш `MCX44-INUSHK`, `Mac Mini M4 Pro
     (24/512)`). Категория угадывается по подстроке названия
     (`_CATEGORY_RULES`, `bsa_parser.py:198`).
   - Строки-заголовки (`## Секция`) и комментарии (`#`) парсер пропускает —
     ставить их для читаемости файла, как в эталоне.
   - **iPad, Apple Watch, AirPods, MacBook, старые iPhone парсер СЕЙЧАС НЕ
     разбирает** — этих категорий у BSA в тексте много (см. выгрузку
     18.08.2026, там огромные блоки iPad с точными SKU по вариантам), но
     `import_bsa.py` их не трогает. Если владелец захочет сверять и их —
     это НОВАЯ функция парсера по образцу `parse_mac`, не забыть предупредить,
     что это расширение объёма, а не то же самое задание.
   - Сохранить новый файл как `data/bsa_YYYY_MM_DD.txt` /
     `data/bsa_mac_YYYY_MM_DD.txt` (дата — дата выгрузки, не дата запуска).

4. **Разобрать и проверить `failed`.** Быстрее всего — маленький скрипт или
   REPL:
   ```python
   from app.services.bsa_parser import parse, parse_mac
   items, failed = parse(open("data/bsa_2026_08_18.txt", encoding="utf-8").read())
   macs, failed_mac = parse_mac(open("data/bsa_mac_2026_08_18.txt", encoding="utf-8").read())
   print(len(items), len(macs), failed, failed_mac)
   ```
   Ноль `failed` — не самоцель: если строка реально мусор (не товар), её место
   не в txt-файле вообще, а не в списке failed.

5. **Обновить `import_bsa.py`**, чтобы читал новые файлы (сейчас имена дат
   захардкожены в `main()`, `import_bsa.py:195-196` — самый ленивый вариант:
   поменять две строки на новую дату; чуть лучше — принять дату аргументом,
   но это уже вкусовщина, не обязательно).

6. **Прогнать БЕЗ `--confirm`** (dry-run — так по умолчанию) на проде:
   ```bash
   ssh iseller "docker compose -f /opt/techshop/docker-compose.prod.yml exec -T backend python -m app.scripts.import_bsa"
   ```
   Показать пользователю вывод (создан/обновлён/без изменений/без фото) —
   владелец подтверждает руками, это НЕ автоматическое применение.

7. **Только после подтверждения — `--confirm`.** На еженедельной сверке
   почти всегда нужен `--prices-only`: без него скрипт заводит новые карточки
   под каждую новую комбинацию память/регион/ASIS (02.09.2026 таких было 102
   против 40 реальных изменений цены), а состав каталога владелец ведёт сам.
   `--diff` печатает «было → стало» построчно — это и есть то, что владелец
   утверждает. Скрипт пишет напрямую в
   прод-БД через SQLAlchemy, в обход HTTP/админки — сделать `pg_dump` бэкап
   перед этим не помешает, если давно не было `update-server.sh` (он бэкапит
   на каждом деплое, но этот скрипт от деплоя не зависит и может запускаться
   отдельно).

8. **Посты канала — отдельный шаг, следом не идёт.** Цены в Mini App
   подтянутся из БД сами, а `@isellerhub` продолжит показывать старые, пока
   не применишь план `price_channel`. Это делается из админки («Прайс
   канала») или командой на проде:
   ```bash
   ssh iseller "docker compose -f /opt/techshop/docker-compose.prod.yml exec -T backend python -c \"
   from app.db.session import SessionLocal
   from app.services import price_channel
   db = SessionLocal()
   slugs = [p.slug for p in price_channel.build_plan(db) if p.action == 'update']
   print(price_channel.apply_plan(db, slugs=slugs))
   \""
   ```
   `build_plan` ничего не отправляет — сначала смотреть его вывод.

   **Фильтр по `action == 'update'` здесь не косметика.** Сдвиг цен меняет
   длину строк, а секция iPhone режется на посты по длине текста — от этого
   в плане появляется `action == 'create'` на новую страницу
   (`price_iphone_p3` 02.09.2026). Это НОВЫЙ пост в канале, а не правка
   существующего: спрашивать владельца отдельно, «обновить цены» такого не
   подразумевает.

   Все посты секций получают `action == 'update'` даже без единого изменения
   цены — в тексте стоит дата, и она меняется ежедневно. Это нормально.
