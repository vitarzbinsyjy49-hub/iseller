## 0. Что строим и зачем

**Цель владельца.** Один современный интерфейс, с которого можно вести магазин,
склад и операционные задачи — и с компьютера, и с телефона. Ориентир: ~98%
операционной работы делать, не выходя из Telegram (Mini App / бот / личка с
ботом).

**Что это технически.** Развитие и замена текущей админки (`admin/`) — не
стройка с нуля и **не трогая бэкенд, БД, бота и витрину**. Ядро здоровое (см.
§6). Меняется слой интерфейса и добавляются два новых модуля (склад, трекер
задач).

**Кодовое имя** в существующих документах — **Dexo** (`docs/context/admin-audit.md`
писался «перед решением переносить панель управления в Dexo»).

## 1. Текущая архитектура (менять нельзя без явного решения)

```
                    ┌─────────────┐
   браузер / ТГ ───▶│  admin (SPA)│──HTTP /api──┐
                    └─────────────┘             │
                                                ▼
   Mini App (витрина) ──HTTP /api──▶  ┌──────────────────┐
                                      │ FastAPI backend  │──▶ PostgreSQL
                                      │ (app.main:app)   │        ▲
                                      └───────┬──────────┘        │
                                              │                   │
             ┌────────────────────────────────┼───────────────────┘
             │                                │
   синхронно │ telegram_publisher.call()      │ enqueue() пишет строку
             ▼                                ▼ в notifications ТОЙ ЖЕ транзакцией
      Telegram Bot API                 ┌──────────────┐
        (канал @isellerhub)            │ сервис `bot` │  отдельный контейнер,
                                       │ long polling │  python -m app.scripts.bot_polling
                                       └──────┬───────┘
                                              │ drain(): раз в ≤30с забирает
                                              ▼ pending-уведомления и шлёт
                                       клиент в личке с ботом
```

**Стек:** FastAPI + PostgreSQL 16; `admin/` и `frontend/` (витрина) — отдельные
Vite+React SPA; Caddy — реверс-прокси и TLS. Прод: один VPS `158.255.1.248`,
домены `*.158.255.1.248.sslip.io`, деплой `bash update-server.sh` (tar-синк
дерева + пересборка compose; **добавляет и заменяет, никогда не удаляет**;
серверный `.env` не перезаписывается).

**Грабли инфраструктуры, которые касаются и новой панели:**

| факт | следствие для Dexo |
|---|---|
| Сеть VPS режет Telegram в обе стороны. Исходящие — через Cloudflare WARP (`TELEGRAM_PROXY_URL`), вебхук не работает, бот на **long polling** | Никаких новых схем доставки в Telegram. Всё исходящее — через существующий `telegram_publisher` (канал) или очередь `notifications` (личка). |
| **Экземпляр бота ровно один.** Два `getUpdates` по одному токену → `409 Conflict` | Нельзя поднимать второй процесс, который сам ходит в Telegram. Своего планировщика (cron/celery/APScheduler) в проекте нет и заводить не нужно — фоновые задачи цепляются к тику бота. |
| В канал Telegram пускает **только `url`-кнопки**; `web_app`-кнопка отвергает весь пост | Кнопки постов канала ведут на `t.me/<bot>?start=<payload>`, бот ловит payload и открывает нужный экран Mini App настоящей web_app-кнопкой. |
| Telegram не скачивает медиа с `*.sslip.io` сам (подтверждено A/B 19.08.2026) | Любая своя загрузка (`/api/uploads/...`) уходит в Telegram **multipart-байтами**, не URL-строкой. Уже реализовано в `telegram_publisher`; новая панель просто передаёт `image_url` как есть. |
| Новые колонки в существующих таблицах создаёт не `create_all`, а мини-миграции в `app/main.py` (`_apply_demo_migrations`) | Добавляешь колонку в таблицу, которую читают фоновые задачи бота (`notifications`, `product_favorites`, `carts`, `users`, `fx_rate_history`) — **обязана попасть в `REQUIRED_SCHEMA` в `app/scripts/bot_polling.py`**, иначе бот падает `UndefinedColumn` на первом тике после деплоя. Тест `test_required_schema_covers_every_mini_migration_column` держит списки сомкнутыми. |

## 2. Как операционные задачи выполняются сегодня

### 2.1 Заявки (лиды) — `models/lead.py`, `api/leads.py`, `api/admin_crm.py`

- Таблица `leads`. Ключевые поля: `status`, `lead_type`, `source`,
  `assigned_to`, `manager_comment`, `meta` (JSON — состав зависит от типа),
  `items_count` / `estimated_total` / `currency`, `idempotency_key` (UNIQUE,
  защита от дублей при повторной отправке формы).
- **Воронка статусов** (`admin/src/ui.ts::STATUSES`):
  `new → contacted → confirming → confirmed → in_progress → reserved →
  completed / cancelled`. Старые заявки могут стоять на прежних пяти статусах —
  задним числом их не меняем.
- **Типы** (`LEAD_TYPES`): `general, product, trade_in, b2b, wholesale, cart,
  price_offer` («нашли дешевле»), `sell_item` (предложение товара на выкуп).
  Для каждого типа `meta` содержит свой набор полей; их локализация и порядок
  отображения — в `admin/src/ui.ts::leadMetaRows` / `META_KEY_RU`.
- **Снапшот состава.** У заявки из корзины состав зафиксирован на момент
  оформления и намеренно не редактируется; отдельно показывается сравнение с
  актуальным каталогом (цена могла уйти).
- **Смена статуса** (`PATCH /api/admin/leads/{id}`): в той же транзакции
  `enqueue()` кладёт уведомление клиенту в очередь `notifications`. Менеджер не
  ждёт Telegram; падение Telegram не роняет CRM.
- **Алерт менеджеру** (новая заявка, `price_offer`, `sell_item`, отмена
  пользователем): тоже через очередь, `chat_id = admin_chat_id()` из
  `settings.ADMIN_TELEGRAM_ID`. **Это уже работающий канал «в личку
  администратору»** — на нём же строится модуль F.

### 2.2 Публикация в канал — ТРИ РАЗНЫЕ модели постов под одним словом «пост»

Это главный источник путаницы в старой панели (см. `admin-audit.md` §3.8).
Новая панель должна свести их в одну ментальную модель для пользователя.

| | «Посты» (редакционные) | «Прайс канала» | «Посты канала» (инфо) |
|---|---|---|---|
| код | `api/posts.py` | `api/price_posts.py` + `services/price_posts.py` + `price_channel.py` | `api/price_posts.py` (`/info/*`) + `services/info_posts.py` |
| текст пишет | AI или человек | генератор из каталога БД | человек в панели |
| статусы | `draft → approved → published / rejected` | `draft / published / outdated / error` | те же, что у прайса |
| правка после публикации | сейчас 409 запрещена (класс А починен 2026-08-11 — теперь редактирует тот же `message_id`) | обновляет тот же `message_id` | обновляет тот же `message_id` |
| кнопки | `button_spec` (описание, не готовая клавиатура) | есть | есть, конструктор кнопок (`/info/button-kinds`) |
| медиа | `image_url` → `sendPhoto` multipart | — | rich: `<img>` внутри `rich_html` |
| rich-контент | `rich_html` (Bot API 10.1/10.2): таблицы, `<details>`, заголовки | — | `rich_html` + `/info/rich-preview` |

**Инварианты, которые легко сломать:**

- Пост публикуется **один раз**, дальше редактируется на том же `message_id`.
  Связь «раздел ↔ сообщение» держит стабильный `slug` (`channel_posts.slug`,
  UNIQUE). Потерять slug = потерять сообщение и выложить дубль.
- Источник прайса — **каталог в БД**, не XLSX. Пост обязан совпадать с тем, что
  покупатель видит в Mini App.
- Инфо-пост с маркером `[уточнить]` система публиковать **отказывается**.
- `published_body` хранит то, что реально ушло в канал — иначе нельзя честно
  ответить «изменилось ли что-то».
- `button_spec` хранит ОПИСАНИЕ кнопок (`[{text, kind, value}]`), а не готовый
  Bot API keyboard: ссылка на менеджера/канал живёт в настройках и может
  смениться — тогда все посты подхватывают новую.
- Публикация идёт **синхронно**: панель → backend → `telegram_publisher.call()`
  → Bot API. Ошибка Telegram приходит наверх как 502. `telegram_publisher`
  делает retry и обрабатывает 429; автотестов, бьющих в настоящий Bot API,
  нет — непроверенную rich-разметку надо один раз отправить в тестовый чат
  руками.
- **Ни один экран старой панели не блокирует кнопку на время запроса** —
  двойной клик «Опубликовать» уходит в Telegram дважды. Новая панель обязана
  дизейблить действие до ответа.

Публичный интерфейс `services/telegram_publisher.py`:
`send_message`, `send_photo`, `edit_message`, `edit_caption`,
`edit_reply_markup`, `send_rich_message`, `edit_rich_message`, `pin_message`,
`publish_post`, `delete_message`. Исключения: `TelegramPublishError`,
`TelegramRateLimited`, `TelegramContentTooLong`.

### 2.3 Уведомления клиенту — очередь outbox (`models/notification.py`, `services/notifications.py`)

- Producer `enqueue(...)` пишет строку в `notifications` **той же транзакцией**,
  что и событие. В сеть не ходит.
- Consumer — функция `drain(db, limit=20)` внутри тика бота (`bot_polling.py`),
  раз в ≤30 с.
- `dedupe_key` UNIQUE — **единственная** защита от дублей, держит БД.
- Доставка **at-least-once**: `sent` ставится ПОСЛЕ отправки.
- Постоянные ошибки (`bot was blocked`, `chat not found`) → сразу `failed`,
  попытки не тратятся. Временные → до `MAX_ATTEMPTS = 5`.
- Тихие часы напоминаний о корзине — 22:00–10:00 МСК (фиксированный сдвиг).
- Без `TELEGRAM_BOT_TOKEN` очередь **не наполняется вовсе** (иначе первый
  запуск с токеном вывалил бы на людей всю историю).
- `kind ∈ (lead_status, cart_reminder, favorite_price)` — расширять здесь и в
  `NOTIFICATION_KINDS`.

### 2.4 Каталог, товары, импорт — `api/admin_crm.py`, `api/imports.py`

- **Import Center** (`/api/admin/import/batch/preview` → `.../confirm` с
  `job_id`, диффом, отчётом по файлам, выгрузкой ошибок в CSV, идемпотентным
  повтором) — лучшая часть старой панели, эталон UX для импорта. Сохранить.
- Инлайновая правка цены и остатка, массовые действия
  (`/products/bulk-action`), отдельная правка остатка
  (`PATCH /products/{id}/stock` — в старой панели **не вызывается**).
- Фото: массовая загрузка по SKU (`/products/{id}/images/bulk`,
  `/uploads/products/images-zip`), выбор главной, реордер, аудит покрытия
  (`/photo-coverage`), сопоставление групп изображений
  (`/import/image-groups/preview|confirm`).
- Навигация каталога **только из данных** — списка категорий в коде нет
  (`services/catalog_nav.py`); Dyson — бренд, не категория. Подробности в
  корневом `CLAUDE.md`.
- Порядок выдачи каталога — один на всё, `services/ranking.py`, приоритет
  берётся из порядка плиток главной (`home_categories.position`).

### 2.5 Главная витрины — `api/home.py`

- **Плитки категорий** (`action_type` + `action_value`) слушаются из панели
  полностью. Правило видимости (пустая плитка не показывается, категория без
  плитки добавляется сама) — в `GET /home`, описано в `CLAUDE.md`.
- **Баннеры — CRUD жив, но вид ему не подчиняется** (`admin-audit.md` §4.1):
  картинка и фон баннера определяются кодом витрины (`Home.tsx::curatedPromo`
  подбирает картинку по ключевым словам заголовка). Переименовал баннер —
  потерял картинку. **Это дыра, которую Dexo должен закрыть:** вид баннера
  (кадрирование, позиция, фон, читаемость текста поверх) обязан стать
  управляемым содержимым, а не константой в бандле витрины.

### 2.6 Клиенты, лояльность, промокоды

- `api/admin_users.py`: список пользователей, карточка, ручное начисление
  баллов (`POST /users/{id}/loyalty`), уровни (`/loyalty/levels` — в старой
  панели зашиты в `Customers.tsx`, эндпоинт не вызывается).
- `api/admin_promo.py`: CRUD промокодов, список погашений.
- Механика баллов/уровней/кэшбека — `services/loyalty.py`,
  `docs/context/cart-and-loyalty.md`.

### 2.7 Аналитика, AI-логи, аудит

- `GET /api/admin/dashboard`, `/analytics`, `/ai-logs`, `/stats`.
- `AuditLog` (`models/audit.py`) пишется на все опасные действия; эндпоинт
  `GET /api/admin/audit` есть, **старая панель его не показывает** — Dexo
  должен дать журнал действий в UI.

## 3. Как панель соединена с ботом — точно

**Прямой связи нет.** Панель говорит только с backend по HTTP. Бот и витрина
читают ту же БД. Заменить интерфейс можно, ничего в боте и витрине не трогая
(`admin-audit.md` §2).

Два канала в Telegram устроены по-разному:

1. **Уведомления (клиенту и менеджеру)** — асинхронно, через таблицу
   `notifications`. Панель/бэкенд только пишут строку; шлёт сервис `bot`.
   Устойчиво к падению Telegram.
2. **Публикации в канал** — синхронно, `telegram_publisher` из процесса
   backend. Ошибка видна сразу как 502.

**Аутентификация панели** (`api/auth.py`, `api/deps.py`, `admin/src/ui.ts`):

- `POST /api/auth/admin/login` (email+пароль) → пара `{access_token,
  refresh_token}`. `access` живёт `ACCESS_TOKEN_MINUTES` (30), `refresh` —
  `REFRESH_TOKEN_DAYS`.
- Субъект access-токена админа — `admin:<...>`; проверяет
  `get_current_admin` (Depends на всех админ-роутерах). Токен пользователя
  витрины — `user:<id>`, другая проверка (`get_current_user`).
- `refresh` **одноразовый** — повтор тем же refresh-токеном отклоняется как
  кража. Клиентский `refreshAccessToken()` шлёт ровно один запрос на все
  параллельные 401.
- Токены — в `sessionStorage` (`admin_access_token` / `admin_refresh_token`).
  `apiGet` / `apiSend` / `apiUpload` сами делают прозрачный refresh на 401.
- `POST /api/auth/admin/dev` (вход без пароля) — только `DEV_MODE=true` и
  только с localhost; на боевом домене маршрут отдаёт 404.

**База API:** всё под префиксом `/api`. Caddy проксирует `admin.<домен>` на
контейнер `admin`, `/api/*` — на backend.

**Дисциплина схемы (обязательно соблюдать):**

- Новые колонки в СУЩЕСТВУЮЩИХ таблицах — только `ALTER TABLE ... ADD COLUMN
  IF NOT EXISTS` в `app/main.py::_apply_demo_migrations`.
- Колонка в таблице, которую читают фоновые задачи бота → ещё и в

- Кириллический SQL на прод — только через `scp` файла, не пайпом из

## 7. Целевой продукт — декомпозиция

Каждый подпроект — свой цикл: бриф → план → реализация → тесты → деплой.
Порядок: **A первым** (фундамент), дальше самый болезненный из B–F.

### A. Оболочка панели (фундамент)
**Скоуп:** адаптивная (телефон + десктоп), современный визуальный язык,
настоящий роутинг с адресами экранов, навигация по задачам, а не по 12
вкладкам. Дизайн-токены и компонентная база. Обработка 401/refresh (уже есть в
`ui.ts` — перенести), дизейбл действий на время запроса, показ ошибок вместо
«глухих» `.catch(() => {})`.
**На чём строить:** текущий `admin/src/ui.ts` (API-хелперы, refresh), список
эндпоинтов §4.
**Готово, когда:** на телефоне и десктопе работает вся текущая
функциональность старой панели, у каждого экрана есть URL, есть тесты.

### B. Склад (новый модуль)
**Скоуп:** остатки, приёмки, движения (приход/расход/списание/перемещение),
инвентаризация, алерты «заканчивается». Связь с `products.stock` /
`products.is_limited`.
**На чём строить:** `PATCH /admin/products/{id}/stock` уже есть;
`services/availability.py`; мерчандайзинг из выгрузки упомянут в
`releases.md` как «мелочь по случаю».
**Новое:** таблицы движений склада, эндпоинты приёмки/списания, отчёт
«ниже минимума». Решить: источник правды по остатку — ручной ввод, импорт из
XLSX-выгрузки поставщика, или оба.
**Готово, когда:** остаток в карточке товара витрины перестаёт быть ручным
полем; есть журнал движений и алерты.

### C. Заявки как процесс (развитие раздела)
**Скоуп:** канбан/воронка по `status`, ответственный (`assigned_to`),
SLA/таймеры, полная история переходов и комментариев, быстрые действия
(позвонить, написать, забронировать). Разные виды заявок (`lead_type`) —
разные карточки.
**На чём строить:** `leads`, `PATCH /admin/leads/{id}`, `leadMetaRows`,
очередь уведомлений клиенту уже дергается на смене статуса.
**Новое:** модель истории статусов (если ещё нет отдельной таблицы), поля
SLA, представление «канбан».

### D. Студия контента (развитие «Постов канала»)
**Скоуп:** один конструктор поста с живым предпросмотром (обычный текст /
фото+подпись / rich-HTML), расписание публикаций, единое место для постов
канала и прайс-постов, конструктор `url`-кнопок с подстановкой deep link.
Счётчики лимитов (1024 с картинкой / 4096 без / 32768 rich).
**На чём строить:** `api/posts.py`, `api/price_posts.py`,
`services/price_posts.py`, `services/info_posts.py`, `/info/rich-preview`,
`telegram_publisher`, `docs/context/channel-posts.md`.
**Осторожно:** инвариант «один message_id, дальше правки»; slug; `[уточнить]`;
дизейбл кнопки на время публикации; rich-разметку проверять в тестовом чате.
**Про расписание:** отдельного планировщика заводить нельзя (§1). Отложенная
публикация = строка в БД + проверка в тике бота, как у очереди уведомлений.

### E. Операционные задачи (новый модуль)
**Скоуп:** лёгкий трекер: задача привязана к сущности (эта заявка, этот товар,
этот поставщик, этот пост), статус, срок, ответственный, чек-листы. Не Jira —
«напоминалка с контекстом».
**Новое:** таблица задач с полиморфной ссылкой на сущность, эндпоинты CRUD,
виджет «мои задачи на сегодня» на дашборде. Просроченная задача может падать
менеджеру в личку через ту же очередь.

### F. Пульт в Telegram-личке (новый слой поверх бота)
**Скоуп:** согласования и быстрые действия падают администратору в ЛС бота,
он жмёт inline-кнопку — действие выполняется. Примеры: «новая заявка →
[Взять в работу] [Отклонить]»; «пост готов → [Опубликовать] [Правки]»;
«товар заканчивается → [Заказать] [Скрыть с витрины]».
**На чём строить:** канал «в личку администратору» уже есть
(`admin_chat_id()` из `settings.ADMIN_TELEGRAM_ID`, очередь `notifications` с
полем `keyboard`). Бот уже принимает `callback_query`? — проверить в
`services/telegram_bot.py` / `bot_polling.py`; если нет, добавить обработчик
callback'ов с проверкой, что нажал именно администратор.
**Новое:** реестр «действий по кнопке» (callback data → операция над
сущностью), идемпотентность (повторное нажатие), аудит. Уважать: один
экземпляр бота, никаких новых процессов, всё через существующий тик.
**Замечание про формулировку «ты можешь писать мне в личку»:** сейчас в
Telegram пишет **бот**, не ИИ. Модуль F — это довести бота до двусторонних
быстрых действий; ИИ-ассистент (черновики постов, подсказки) может быть
отдельной надстройкой над backend, но это не про доставку в Telegram.

## 8. Требования, общие для всех подпроектов

**Обязательно:**

- Адаптив: один интерфейс, телефон и десктоп. Плотные таблицы → карточный
  режим на узком экране; главное действие всегда в зоне видимости.
- Настоящие маршруты: у каждого экрана URL, «назад» работает, F5 не
  разлогинивает (токены уже в `sessionStorage`).
- Не ломать контракт backend: витрина (Mini App) и бот читают ту же БД. Любое
  изменение схемы — по §5.
- Тесты: старая панель их не имеет вовсе. Dexo — с тестами (минимум: типы +
  сценарные тесты ключевых экранов).
- Дизейбл действий на время запроса; показ ошибок; никаких `.catch(() => {})`.
- Лимиты Telegram и multipart-медиа — не трогать, `telegram_publisher` уже всё
  делает; панель передаёт данные, не бьёт в Bot API напрямую.

**Не делать (guardrails):**

- Не менять модель «long polling, один экземпляр бота».
- Не заводить cron/celery/APScheduler — отложенные задачи через тик бота.
- Не нарушать инварианты постов канала (`slug`, один `message_id`,
  `[уточнить]`, `published_body`).
- Не слать состав/суммы заявок в открытый канал (в `_send` очереди нет
  fallback на канал — и не должно быть).
- Не хардкодить списки категорий/брендов (см. `CLAUDE.md`).

**Роли и права — открытый вопрос.** Владелец пока не зафиксировал: только он,
он + 1–2 помощника, или команда с ролями (менеджер / кладовщик / контентщик).
От этого зависит, нужна ли модель прав и разграничение экранов. До ответа —
проектировать с одним админом, но не закладываться на «навсегда один».

## 9. Порядок работ и приёмка

1. **A (оболочка)** — до паритета со старой панелью по функциям, плюс адрес у
   каждого экрана и тесты.
2. Дальше — приоритетный из **B / C / D** (спросить владельца).
3. **E**, затем **F**.
4. Каждый подпроект: бриф → план (`docs/superpowers/`) → реализация → `cd admin
   && npx tsc --noEmit && npm run build` + новые тесты → деплой
   `bash update-server.sh` (только из Git Bash).
5. После деплоя проверять живьём на телефоне, а не только в dev-браузере
   (класс А дефектов прошёл именно потому, что «тесты прошли» ≠ «работает в
   UI»).

**Проверки перед «готово» (весь проект):**
```
cd backend && python -m pytest -q
cd frontend && npx tsc --noEmit && npx vitest run && npm run build
cd admin && npx tsc --noEmit && npm run build   # + vitest, когда появится
```
