# ТЗ 04 — Полка «Под заказ» отдельным блоком

**Оценка:** M (1–2 дня) · **Файлы:** `frontend/src/pages/Catalog.tsx`,
новый `frontend/src/lib/shelfSplit.ts` + тест, `frontend/src/components/ProductCard.tsx`
(без правок, только использование) · **Референс:** `frames/05-feed.jpg`

---

## 1. Что у Лавки

Посреди обычной выдачи стоит серый скруглённый контейнер со своим заголовком:

```
┌─ Может, ещё кое-что? ───────────────── [Все ›] ─┐
│  из большой Лавки за 50–80 мин                  │
│  [товар] [товар] [товар] →                      │
└─────────────────────────────────────────────────┘
```

Товары с **другим сроком доставки** не подмешаны в общую сетку, а вынесены в
собственный блок с честной подписью прямо под заголовком. Человек видит цену и
понимает условие одновременно — не после добавления в корзину.

Это самый ценный приём из всей записи: он решает не оформительскую, а
продуктовую задачу — как продавать то, что нельзя получить так же быстро, как
остальное, и не соврать при этом.

## 2. Что у нас сейчас

В каталоге все режимы доступности лежат в одной сетке. Режим виден только
подписью на карточке (`availabilityText()` → «В наличии» / «Предзаказ» / «Под
заказ»), серым мелким текстом.

Итог: человек листает выдачу, где вперемешку лежит то, что можно забрать
сегодня, и то, что приедет через недели. Наличие — сильнейший фактор выбора в
технике, и сейчас он спрятан в подписи 11px.

Порядок выдачи уже частично это учитывает: `services/ranking.py` ставит
`in_stock` первым ключом сортировки. То есть данные к разделению готовы —
не хватает визуальной границы.

## 3. Что делаем

### 3.1 Разделение выдачи

При сортировке **«Популярные»** (дефолт) и без активных сужающих фильтров
выдача каталога делится на две группы:

| группа | режимы | подача |
|---|---|---|
| основная | `in_stock`, `limited` | обычная сетка, как сейчас |
| «Под заказ» | `preorder`, `on_request` | отдельный блок ниже основной сетки |

`out_of_stock` и `unavailable` в каталог не попадают (их отфильтровывает
backend) — если попадут, идут в «Под заказ» как наименее срочное.

### 3.2 Блок «Под заказ»

- Контейнер `rounded-xl2 bg-mutedbg p-4 -mx-4 px-4` — **подложка тоном**, как у
  `QuickScenarios`, без тени и обводки: это не карточка товара и спорить по весу
  с настоящими карточками не должно.
- Заголовок `Под заказ` (`text-[17px] font-bold`) + подпись под ним:
  `Привезём под вас — срок и цену менеджер подтвердит в заявке`.
  **Никаких конкретных сроков в днях**: backend их не отдаёт, а «7–14 дней» —
  это обещание за счёт магазина.
- Внутри — та же сетка карточек, что и в основной выдаче (не лента: в каталоге
  человек уже листает вертикально, вторая ось прокрутки внутри вертикальной
  выдачи ловится пальцем плохо).
- Если под заказ ничего нет — блока нет.
- Если **вся** выдача под заказ (например, узкая категория) — блока тоже нет,
  карточки идут обычной сеткой. Заголовок «Под заказ» над экраном, где больше
  ничего и не бывает, ничего не сообщает.

### 3.3 Когда разделения НЕ происходит

- при явной сортировке (`price_asc`, `price_desc`) — человек попросил порядок по
  цене, и разрывать его группировкой значит не выполнить просьбу;
- при активном фильтре «В наличии» (`in_stock=true`) — группы «под заказ» там
  быть не может по определению;
- в результатах поиска по строке (`query`) — там релевантность важнее режима;
- в лентах на главной и в рекомендациях — они короткие, и блок в 2 карточки
  выглядит как ошибка вёрстки.

## 4. Данные

Backend **не трогаем**. `GET /api/catalog/list` уже отдаёт в каждой карточке
`availability_mode` (`Product.to_card()` → `availability_payload()`), и
фронт делит массив на месте.

Фильтра по `availability_mode` в `/catalog/list` нет и добавлять его в рамках
этого ТЗ не нужно: выдача ограничена `limit=50`, деление одного массива дешевле
второго запроса.

⚠️ **Известное следствие:** при `limit=50` деление происходит внутри уже
усечённой выдачи. Если 50 первых позиций — сплошь «в наличии», блок «Под заказ»
не появится, хотя такие товары в базе есть. Это допустимо (ранжирование
намеренно поднимает наличие наверх), но записать в известные ограничения:
`docs/KNOWN_LIMITATIONS.md`.

## 5. Логика — в `lib/shelfSplit.ts`

```ts
export type Shelves<T> = { main: T[]; onOrder: T[] };

export function splitByAvailability<T extends { availability_mode?: AvailabilityMode | null; in_stock?: boolean }>(
  cards: T[],
  opts: { enabled: boolean },
): Shelves<T>
```

`enabled: false` (сортировка по цене, поиск, фильтр наличия) → всё в `main`,
`onOrder` пуст. Порядок внутри каждой группы **сохраняется исходный** — backend
уже отранжировал, переупорядочивать нельзя.

Тесты:
- пустой вход → две пустые группы;
- `enabled: false` → всё в `main` независимо от режимов;
- смешанный вход → правильное распределение по таблице §3.1;
- карточка без `availability_mode` (старый кэш, фикстура AI) читается по
  `in_stock`, ровно как в `availabilityText()` — **два разных ответа об одном
  товаре на соседних экранах хуже, чем один скучный**;
- вся выдача под заказ → `onOrder` пуст, всё в `main` (правило §3.2);
- порядок внутри групп не меняется.

## 6. Аналитика

```ts
track("order_shelf_shown", { count: onOrder.length, category });
track("order_shelf_product_click", { product_id, position });
```

Нужно, чтобы понять, кликают ли по «под заказ» вообще, или блок работает как
фильтр внимания в одну сторону.

## 7. Крайние случаи

- **Смена категории** — деление пересчитывается вместе с выдачей, без
  собственного состояния и без анимации перескока.
- **Бесконечная прокрутка / «показать ещё»** (если появится) — новая порция
  делится тем же вызовом; блок «Под заказ» остаётся один, внизу, и дополняется.
- **Кэш выдачи** не должен хранить уже разделённый результат — кэшируем сырой
  массив, делим при рендере.

## 8. Готово, когда

- [ ] В каталоге по умолчанию видно два блока, если в выдаче есть оба режима.
- [ ] При сортировке по цене и при поиске деления нет.
- [ ] Ни в заголовке, ни в подписи блока нет ни одного срока в днях.
- [ ] `shelfSplit.test.ts` зелёный, включая кейс карточки без `availability_mode`.
- [ ] Ограничение про `limit=50` записано в `docs/KNOWN_LIMITATIONS.md`.
- [ ] Проверено на реальном каталоге прода, а не на фикстуре.
