## 1. Аутентификация и доступ — самое важное отличие от вашей платформы

**Ролей нет. Пользователь админки один, и он не строка в БД.** [код]

```
POST /api/auth/admin/login   {email, password}  →  {access_token, refresh_token}
POST /api/auth/refresh       {refresh_token}    →  новая пара
```

- логин и пароль — **переменные окружения** `ADMIN_EMAIL` / `ADMIN_PASSWORD`
  (`app/core/config.py`), никакой таблицы сотрудников нет;
- субъект токена — строка `admin:<email>`. `get_current_admin` (`api/deps.py`)
  проверяет только префикс `admin:` и возвращает email. Никакой проверки прав
  по действию нет: **любой админ-токен может всё**;
- `ACCESS_TOKEN_MINUTES = 30`, `REFRESH_TOKEN_DAYS = 14`; refresh одноразовый,
  повторное использование фиксируется в аудите (`refresh_token_reuse_rejected`
  — на проде уже 1 раз сработало) [прод];
- лимит на подбор пароля: `ADMIN_LOGIN_RATE_LIMIT_PER_MINUTE = 5`,
  in-memory (Redis не подключён). На проде за всё время: 47 успешных входов,
  41 неудачных, 20 отбитых лимитером [прод];
- клиентские токены — другой субъект (`user:<id>`), выдаются по
  `POST /api/auth/telegram` с проверкой `init_data`. Смешать нельзя: `/admin/*`
  на клиентском токене отдаёт **403**, не 401.

Для вас практический вывод: **весь блок «сотрудники, роли, приглашения,
настоящий актор» у нас отсутствует целиком**, и это не деградация переезда, а
приобретение. Аудит уже пишется, но актор в нём — либо `admin:<email>` из
`.env`, либо `tg:<id>` клиента.

**Аудит** (`audit_logs`, 736 записей на проде) [код+прод]:

```
actor   VARCHAR(64)   tg:<id> | admin:<email> | system
action  VARCHAR(64)   индексируется
detail  TEXT
ip      VARCHAR(64)
created_at
```

Реально встречающиеся `action` на проде: `admin_login`, `admin_login_failed`,
`admin_login_rate_limited`, `login`, `register`, `lead_status_changed`,
`products_bulk_activate|deactivate|delete`, `import_batch_preview|confirm|cancel`,
`info_post_created|edited`, `info_posts_generated|published`,
`price_posts_publish`, `post_approved`, `post_rejected`, `promo_code_created`,
`product_photo_enrichment`, `product_photo_color_correction`,
`refresh_token_reuse_rejected`.

`GET /api/admin/audit` существует, **экрана в панели нет** — журнал пишется, но
из UI его никто никогда не видел.

Это главная ловушка при проектировании экранов. Поля:

| | `kind=news` («Посты») | `kind=price` / `price_nav` («Прайс канала») | `kind=info` («Посты канала») |

При проектировании единого конструктора это надо свести в одну сущность —
поля для этого в таблице уже есть.

### Что нельзя сломать при любом редизайне

1. **`slug` → один `telegram_message_id` на всю жизнь поста.** Публикация не
   создаёт новое сообщение, а редактирует существующее. На проде 20 постов,
   19 с `message_id`, все живые (полный список ниже, §7);
2. **`published_body`** — то, что реально ушло в канал; расхождение с `body`
   означает «есть неопубликованные правки»;
3. **`button_spec`** — декларация кнопок, из которой строится `reply_markup`.
   В канале допустимы **только `url`-кнопки**: `web_app`-кнопка отвергает пост
   целиком (`BUTTON_TYPE_INVALID`), обход — deep link `t.me/<bot>?start=<payload>`;
4. **`[уточнить]`** — маркер незаполненного места в инфо-посте; публикация с ним
   не выпускается;
5. **Подпись к фото в Telegram — 1024 символа**, без фото — 4096.
   `telegram_publisher` режет молча, лимит в UI обязателен.

### Порядок выдачи каталога

Правило живёт в одном месте — `services/ranking.py`, им пользуются каталог,
`/catalog/feed`, поиск и рекомендации:

```
in_stock -> popularity -> позиция категории из плиток -> цена -> id
```

Приор берётся из `home_categories.position` — то есть **порядок плиток главной,
который редактируется в админке, управляет и порядком товаров в каталоге**.
`id` в конце ключа обязателен, иначе Postgres даёт произвольный порядок при
равных ключах (на проде это выводило AirPods наверх «Популярного»).

### Навигация каталога — только из данных

Списка категорий в коде нет и заводить его нельзя: категории и бренды считаются
из активных товаров (`services/catalog_nav.py`). Плитка без товаров не выходит
на главную, категория без плитки добавляется сама, `is_active=False` — осознанное
«скрыть», автодобавление её не воскрешает. Dyson — **бренд**, не категория
(`action_type=brand` → `/catalog?brand=Dyson`).

## 4. Инварианты интеграции: как админка связана с Telegram

Прямой связи админки с ботом нет — только через backend. Два канала устроены
**по-разному**, и это принципиально: [код]

```
админка ──HTTP──> FastAPI ──> PostgreSQL
                     ├──> notifications (очередь) ──> сервис bot ──> клиент
                     └──> telegram_publisher ──> Bot API ──> канал   (СИНХРОННО)
```

- **уведомления клиентам** асинхронны: смена статуса заявки пишет строку в
  `notifications` с `dedupe_key UNIQUE`, отдельный процесс `bot` разбирает
  очередь на своём тике. Telegram лежит — изменение не потеряно. Сделано верно;
- **публикации в канал** синхронны: ошибка Telegram приходит в админку как 502.
  Ни один экран не блокирует кнопку на время запроса — **двойное нажатие
  «Опубликовать» уходит в Telegram дважды**.

`notifications`: `chat_id, kind, text, keyboard (JSON), dedupe_key UNIQUE,
status, attempts, last_error, sent_at`. **Поле `keyboard` уже есть** — фундамент
под «пульт в личке» (ваш модуль F) заложен, но не использован.

### Бот: чего в нём нет

Процесс `bot` (`app/scripts/bot_polling.py`) — long polling, шаг ≤30 с.
Отдельного планировщика (cron/celery/APScheduler) в проекте нет и заводить
нельзя: каждый новый постоянный процесс — ещё один повод поймать 409 Conflict
вторым экземпляром бота. Фоновые задачи цепляются к тику: [код]

| задача | интервал |
|---|---|
| разбор очереди `notifications` | каждый тик, пачкой `OUTBOX_BATCH` |
| скан корзин (напоминания) | `CART_REMINDER_SCAN_MINUTES = 30` |
| скан избранного (цена/наличие) | `FAVORITE_WATCH_SCAN_MINUTES = 60` |
| синк курса ЦБ РФ | попытка не чаще 1 раза в 5 минут |
| прогрев AI-гейтвея | по интервалу |

**`allowed_updates` = `["message"]`. Обработчика `callback_query` нет вообще.**
Ни одной inline-кнопки бота, нажатие которой что-то меняет в БД, никогда не
существовало — ответ на ваш вопрос 4.7 и часть 7.3.

**`REQUIRED_SCHEMA`** в `bot_polling.py` — список таблиц и колонок, без которых
бот не начинает фоновые задачи. Новая колонка в `users` (её ORM тянет целиком в
скане корзин) обязана попасть в этот список, иначе бот падает `UndefinedColumn`
на первом деплое. Тест `test_required_schema_covers_every_mini_migration_column`
держит список сомкнутым с мини-миграциями `main.py`.

### 7.3 Сценарий «прислал в бота → подтвердил → опубликовал»

**Это пожелание, а не работающий механизм.** Технически он сегодня невозможен:
обработчика `callback_query` в боте нет, `allowed_updates` = `["message"]`
(см. §4). Как это выглядит на самом деле: черновик готовится скриптом или
руками, показывается владельцу **в чате Claude Code** (не в Telegram), он
говорит «ок» текстом, публикацию вызываю я — командой. Подтверждение кнопкой в
личке существует только в замысле.

Поэтому ваш модуль F — не «ещё один интерфейс», а **первая реализация того
контура, который владелец уже считает своим рабочим процессом**.

### 7.5 Память

Контекст между сессиями держат:
- `CLAUDE.md` в корне репозитория — читается автоматически в начале каждой
  сессии, там инварианты, адреса, деплой и самые дорогие грабли;
- `docs/context/*.md` — детали по темам, читаются по необходимости;
- файлы памяти Claude Code (короткие заметки об окружении: какая оболочка, как
  ходить на прод, что кириллический SQL нельзя слать пайпом).

**Что потерялось при смене контекста:** сама переписка файлов 01–06 в ней не
лежала — она жила в чате. Отсюда и ТЗ от 31.08, написанное без учёта переезда.
Меры уже приняты: ваши файлы 05 и 06 и мои ответы 01/03/04 положены в
`docs/handoff/` внутри репозитория, то есть теперь переживают смену сессии.

### 7.7 Боли

- **двойная публикация** от двойного нажатия — ни одна кнопка не блокируется на
  время запроса;
- **502 от Telegram** при синхронной публикации: непонятно, ушло или нет;
- **409 Conflict** при двух экземплярах бота;
- **картинка баннера** теряется при переименовании (§5.4);
- больше всего ручной работы — фото товаров и сверка цен с BSA.
