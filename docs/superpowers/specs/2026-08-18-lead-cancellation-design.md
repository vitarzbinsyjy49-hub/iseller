# Отмена заявки пользователем + уведомления менеджеру о заявках

Дата: 2026-08-18

## Контекст

Пользователь видит свои заявки в «Мои заявки» (`frontend/src/pages/Requests.tsx`,
`GET /leads/my`), но не может ничего с ними сделать — только смотреть статус.
Отменить заявку сейчас может только менеджер из админки
(`PATCH /admin/leads/{id}`, `backend/app/api/admin_crm.py:155`).

Отдельно обнаружилось: менеджер получает Telegram-алерт о НОВОЙ заявке только
для двух типов — `price_offer` (`_notify_owner`, `backend/app/api/leads.py:82`)
и `sell_item` (`_notify_sell_item`, `backend/app/api/leads.py:148`). Обычные
заказы (general/product/cart/trade_in/b2b/wholesale) создаются молча — менеджер
узнаёт о них, только если сам зайдёт в админку. Это расширение объединено с
отменой в одну спеку, потому что технически это одна и та же ось: «менеджер
должен узнавать о событиях жизненного цикла заявки», а не только слушать одну
её половину (смену статуса самим менеджером).

### Что уже есть и переиспользуется

- `LEAD_STATUSES` включает `cancelled` (`backend/app/models/lead.py:18`) — статус
  уже существует и полностью прожит в admin-части: `_notify_status_change`
  (`admin_crm.py:119`) шлёт владельцу сообщение при смене статуса, аудит-лог
  пишется в `AuditLog(action="lead_status_changed", detail="lead=X;from=Y;to=Z")`.
- Frontend `Requests.tsx` уже рисует бейдж `cancelled` → «Отменена»
  (серый, `STATUS_STYLE.cancelled`) — использовать её для пользовательской
  отмены не требует новой вёрстки статуса, только кнопки.
- Admin `App.tsx:737` уже показывает `status_history` с полем `actor` — если
  actor для отмены пользователем будет `user:{id}` (а не `admin:{email}`,
  как сейчас единственный вариант), менеджер увидит в истории, кто именно
  отменил, без единой строчки нового кода в админке.
- `enqueue()` + `notification_templates.py` — общий механизм постановки
  Telegram-уведомлений в очередь (без сети в самом запросе, та же транзакция).

## Backend: эндпоинт отмены

`POST /api/leads/{lead_id}/cancel` (JWT, `backend/app/api/leads.py`), НЕ общий
`PATCH` — пользователь физически не может выставить себе никакой статус,
кроме `cancelled`.

- 404, если заявки нет или `lead.user_id != user.id` (не палим существование
  чужой заявки различием 403/404).
- 400 «Заявку в этом статусе отменить нельзя», если `lead.status` уже
  `completed` или `cancelled`. Отменять можно с ЛЮБОГО из остальных статусов
  (`new/contacted/confirming/confirmed/in_progress/reserved`).
- Иначе: `lead.status = "cancelled"`, `AuditLog(actor=f"user:{user.id}",
  action="lead_status_changed", detail=f"lead={lead_id};from={previous};to=cancelled")`
  — те же поля, что у admin-эндпоинта, поэтому история статусов в админке
  работает без изменений.
- Уведомление менеджеру (новый шаблон `lead_cancelled_by_user_message`,
  см. ниже), `dedupe_key=f"lead:{lead_id}:cancelled_by_user"`.
- Владельца о его же действии НЕ уведомляем повторно (он только что увидел
  результат на экране) — существующий `_STATUS_TEXTS["cancelled"]` в
  `lead_status_message` остаётся как есть и продолжает срабатывать только при
  отмене АДМИНОМ через `admin_crm.py`.

## Backend: уведомление менеджеру о новой заявке

Два места создают заявку, и у них РАЗНАЯ форма транзакции — общий `else`
в одном `create_lead()` не покроет оба:

1. **`create_lead()`** (`leads.py:173`) — одиночные заявки (LeadForm,
   ScenarioChat/Trade-In/B2B/опт, SellItem уже покрыт своей веткой). После
   веток `price_offer`/`sell_item` добавляется `else`-ветка на оставшиеся
   типы (`general/product/trade_in/b2b/wholesale`) — `db.flush()` +
   уведомление + общий `db.commit()`, как у соседних веток.
2. **`POST /cart/checkout`** (`api/cart.py:122`) — заявка из корзины НЕ идёт
   через `create_lead()`, её создаёт `cart_service.checkout()`, и та функция
   уже коммитит транзакцию ДО возврата `(lead, created)` (`services/cart.py:501`).
   Значит, уведомление здесь не может ехать той же транзакцией, что создание
   лида — вешаем его отдельным хуком в `if created:` блоке `api/cart.py`,
   со своим try/except + `db.commit()`, ровно как уже сделано для `_track()`
   в том же блоке (`api/cart.py:174`): не роняем оформление заказа, если
   постановка уведомления в очередь споткнётся.

Оба места используют один и тот же новый шаблон `new_lead_message` в
`notification_templates.py`, по образцу композиции из `lead_status_message`
(строки состава — количество позиций + предварительная сумма для заявки-корзины,
либо название товара для одиночной):

```
🆕 <b>Новая заявка{: тип, если не general}</b>

{состав: товар/корзина}
От: {username или "покупатель"}{, phone}
{message, если есть, обрезанный}

Смотрите в «Заявках» админки.
```

`lead_type` эффективно определяет только заголовок (Trade-In/Опт/Для бизнеса/
Обычная — те же подписи, что `LEAD_TYPE_RU` в admin `ui.ts`, но своя копия на
backend, т.к. общего модуля лейблов между admin и backend нет и заводить его
ради одного словаря не стоит).

`dedupe_key=f"lead:{lead.id}:created"`.

## Frontend: кнопка «Отменить» в «Мои заявки»

В `Requests.tsx`, на карточке заявки — кнопка «Отменить», видима только если
`!["completed", "cancelled"].includes(l.status)`.

- Тап → инлайн-подтверждение внутри карточки («Точно отменить?» / «Да,
  отменить» / «Нет») — без `alert()`, по конвенции проекта (см. `Cart.tsx`,
  «Ни одного alert()»).
- «Да, отменить» → `api(\`/leads/${l.id}/cancel\`, {method: "POST"})`.
  При успехе — обновить статус заявки в локальном стейте на `cancelled`
  (бейдж уже есть, перезагрузка списка не нужна). При ошибке — `toast()`.
  `track("lead_cancelled", {lead_id, lead_type})` — по аналогии с
  `sell_item_submitted`.
- Кнопка/подтверждение — только у ОДНОЙ карточки за раз (обычный `useState`
  с id заявки, которая сейчас в режиме подтверждения).

## Admin

Без изменений в коде — `status_history` уже показывает `actor`.

## Тестовый план

- Backend: `POST /leads/{id}/cancel` — своя заявка переводится в cancelled;
  чужая заявка → 404; повторная отмена уже `cancelled`/`completed` → 400;
  `AuditLog` пишется с `actor=user:{id}`; уведомление ставится в очередь
  (`notifications` таблица) при настроенном `ADMIN_TELEGRAM_ID`.
- Backend: создание заявки типа `general`/`trade_in` через `POST /leads`
  ставит в очередь уведомление менеджеру; оформление корзины через
  `POST /cart/checkout` — тоже (отдельная проверка, отдельный код-путь);
  повторный checkout по тому же `idempotency_key` (`created=False`) уведомление
  не дублирует; `price_offer`/`sell_item` не дублируют его вторым сообщением
  (у них остаётся старое, специфичное).
- Frontend: кнопка не показывается для `completed`/`cancelled`; инлайн-подтверждение
  открывается/закрывается; успешная отмена меняет бейдж на «Отменена» без
  перезагрузки страницы.
