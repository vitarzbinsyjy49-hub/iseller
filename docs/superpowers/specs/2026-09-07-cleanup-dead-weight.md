## 1. Главная ловушка этой работы

**Деплой добавляет и заменяет, но НИКОГДА не удаляет.** Синхронизация — это
`tar x` поверх каталога. Любой файл, удалённый локально, остаётся на сервере
навсегда.

Последствие: `grep` по коду прода будет показывать удалённый модуль как
живой. В сборку он не попадёт, пока на него нет импорта, — но проверять надо
бандл, а не наличие файла.

Поэтому **каждое удаление файла в этом ТЗ имеет парный шаг «убрать на
сервере по SSH»**. Пропустить его — значит оставить ровно ту грязь, ради
которой всё затевалось.

## 2. Ветки

### 2.1 Снять worktree

Две ветки удерживаются живыми worktree и без этого шага не удалятся:

```bash
git worktree list
# C:/iseller-demo/.claude/worktrees/clever-hugle-26134c        [claude/affectionate-proskuriakova-10813a]
# C:/iseller-demo/.claude/worktrees/mystifying-jackson-9b6bcf  [claude/mystifying-jackson-9b6bcf]
```

Имя каталога worktree **не совпадает** с именем ветки внутри него — не
ориентируйся на каталог, смотри в квадратные скобки.

```bash
git worktree remove .claude/worktrees/clever-hugle-26134c
git worktree remove .claude/worktrees/mystifying-jackson-9b6bcf
git worktree prune
```

Если `remove` ругается на незакоммиченные изменения — **остановись и покажи
их владельцу**, не удаляй с `--force`. Обе ветки слиты в `master`, но
незакоммиченное в worktree в `master` не попало по определению.

### 2.2 Удалить локальные ветки

Все четыре слиты в `master` (проверено `git branch --merged master`):

```bash
git branch -d claude/keen-rhodes-e0d5e7
git branch -d claude/clever-hugle-26134c
git branch -d claude/affectionate-proskuriakova-10813a
git branch -d claude/mystifying-jackson-9b6bcf
```

Именно `-d`, не `-D`. `-d` откажется удалять неслитую ветку — это
предохранитель, а не помеха.

### 2.3 Удалить `windows-master` на origin

`git rev-list --count master..origin/windows-master` = **0**: уникальных
коммитов нет, ветка целиком содержится в `master`.

```bash
git push origin --delete windows-master
```

### 2.4 Что НЕ трогать

`feature/photo-coverage-rocketniks` (локальная и на origin) — **оставить**.
Решение владельца от 07.09. Там один неслитый коммит `3603a57` с офлайн-
инструментом подбора фото по Rocketniks API; товары без фото появляются с
каждым импортом, инструмент может ещё пригодиться. Ветка висит в стороне и

## 3. `artifacts/rocketniks` — 71 MB

967 файлов в git: 345 webp, 62 png, 47 jpg скачанных фото, 493 json кэша
API, 2 zip. Выхлоп разового прогона от 24.07. Это 86% веса репозитория.

**Решение владельца: убрать из дерева, историю НЕ переписывать.**

```bash
git rm -r --cached artifacts/rocketniks
rm -rf artifacts/rocketniks
```

Затем в `.gitignore`:

```
artifacts/rocketniks/
```

**Честно про эффект.** Чекаут станет легче на 71 MB, новые прогоны
инструмента больше не попадут в git. Но `.git` как весил ~82 MB, так и
останется: блобы живут в истории. Уменьшить его может только
`git filter-repo` с переписыванием всех SHA и force-push — от этого
осознанно отказались 07.09, через час после первого за три недели успешного
пуша. **Не предлагай filter-repo снова без явного запроса владельца.**

Остальные подкаталоги `artifacts/` (`channel-posts`, `onboarding-content`,
`price-preview`, `bot-restore-backup` — суммарно ~5 MB) **не трогать**: на
`onboarding-content` есть живая ссылка из
`frontend/src/components/onboarding/SceneTrust.tsx:13`.

## 4. GSAP — мёртвая зависимость

`frontend/src/lib/gsapMotion.ts` импортируется **только собственным тестом**

на rAF-моторе `lib/motion.ts` (его тянут 28 файлов). Tree-shaking GSAP из
бандла уже выбрасывает — в `dist` его нет, — то есть вес мы не платим, но
зависимость и модуль висят.

Пришёл коммитами `02ee68d`, `8cd6c9f`, `43b84e5`.

```bash

rm src/lib/gsapMotion.ts src/lib/gsapMotion.test.ts
```

Убедиться, что `package.json` и `package-lock.json` согласованы (два из трёх
коммитов выше как раз чинили их расхождение).

**Парный шаг на сервере** (см. §1):

```bash
ssh iseller "rm -f /opt/techshop/frontend/src/lib/gsapMotion.ts \
                   /opt/techshop/frontend/src/lib/gsapMotion.test.ts"
```

Если владелец решит, что Flip ещё нужен для будущей анимации, — тогда не
удалять, а **довести до реального использования**. Промежуточное состояние
«лежит на всякий случай» — худшее из трёх.

## 6. Что НЕ входит — и почему

Три задачи стояли в плане недели 2 и **отменены данными с прода 07.09**.

### 6.1 Ретеншн `analytics_events` — не нужен

| таблица | строк | размер | первая запись |
|---|---|---|---|
| `analytics_events` | 4 092 | 792 kB | 15.07 |
| `user_product_events` | 251 | 160 kB | 22.07 |

Восемь недель — четыре тысячи строк и меньше мегабайта, темп ~500 строк в
неделю. За год выйдет ~30 тысяч строк и ~6 MB. «Единственная таблица с
неограниченным ростом» — формально верно, практически выдуманная работа.

Хуже: чистка удаляла бы факты воронки, ради которых затевается фаза 1
патча 2.0, **до её начала**. Вернуться к вопросу не раньше, чем таблица
перевалит за миллион строк.

### 6.2 `recompute_popularity` на расписание — вредно

Разбивка `user_product_events` на проде:

```
product_view         202 события, 59 товаров, 16 пользователей
recommendation_click  34            28                4
favorite_remove        6             3                3
lead_created           6             1                3
favorite_add           3             3                3
```

В каталоге **408 активных товаров**, всего пользователей — **33**, заявок —
**9**.

Прогон пересчёта проставил бы `popularity` 59 товарам по кликам 16 человек,
а оставшимся 349 оставил ноль. Это не сигнал ранжирования, это шум — и
выдача станет **хуже** нынешней: сейчас порядок детерминированно опирается
на позицию плитки главной (`services/ranking.py`), то есть на решение,
которое владелец осознанно принимает в админке.

Возвращаться, когда `product_view` наберёт хотя бы несколько тысяч событий
по заметной доле каталога.

### 6.3 Durable-состояние тика — преждевременно

Мотивом было «`recompute_popularity` раз в сутки не переживёт перезапуск
контейнера». Раз сам пересчёт отменён (§6.2), мотива нет. Существующие
задачи тика (прогрев гейтвея 5 мин, скан корзин 30 мин, скан избранного
60 мин, курс ЦБ 5 мин, `drain` каждый тик) от потери состояния при
перезапуске теряют максимум один лишний прогон — это не проблема, а
штатное поведение.

Wall-clock-расписание и вынос длинных задач из цикла опроса понадобятся
фазе 5 (автопостинг в канал) — там и проектировать.

### 6.4 Общий вывод, который важнее трёх пунктов выше

У проекта **33 пользователя**. Всё, что отменено в §6, — инфраструктура под
масштаб, которого нет. Это не про планировщик; это про то, что людей неоткуда
взять, пока не работает атрибуция. Фаза 1 патча 2.0 из «хорошо бы измерять»
превращается в предпосылку всего остального — и, раз неделя 2 сжалась до
одного прогона, начинать её можно на неделю раньше плана.

## 8. Коммит и деплой

Одним коммитом, сообщение в стиле проекта (`chore(уборка): ...`).

**Деплой в этот раз не обязателен** — ни один удаляемый файл в сборку не
входит. Если деплой всё же делается, помни: он не удалит на сервере ничего
из §3–§5, это делается руками по SSH.

Перед деплоем убедись, что в рабочем дереве нет постороннего:
синхронизируется ВСЁ дерево, включая незакоммиченное.
