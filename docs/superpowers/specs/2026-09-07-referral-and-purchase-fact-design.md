> Составлено 07.09.2026 по состоянию `master` = `739d78a`.
> Читать вместе с `docs/context/cart-and-loyalty.md` (баллы и уровни),
> `docs/context/sharing-and-social-proof.md` (deep link'и) и
> `docs/superpowers/specs/2026-08-01-loyalty-design.md` (программа лояльности).

## 0. Зачем

Две задачи, которые нельзя решить по отдельности.

**Первая.** В системе нет факта покупки. Баллы начисляются только вручную из
админки, потому что заявка — не покупка: `estimated_total` оценочный, состав
меняется, фиксации оплаты нет. Это записано в `cart-and-loyalty.md` как
осознанное решение.

**Вторая.** Роудмап обещает пользователям реферальную программу со сроком
«сентябрь». Процент с покупок приглашённого не с чего считать, пока покупки в
системе не существует.

Поэтому сначала появляется факт покупки, и только потом — программа поверх
него. Части 1 и 2 разделены намеренно: часть 1 полезна сама по себе
(автоматический кэшбек покупателю) и обязана уехать первой.

## 1. Снятие запрета на автоначисление — обоснование

`cart-and-loyalty.md` гласит: «Начисление только вручную из админки.
Автоматики на статусе заявки нет намеренно». Этот запрет **снимается
частично**, и важно понимать, почему это не отмена прежнего решения.

Прежний запрет был про статус «заявка создана»: человек нажал кнопку, ничего
не произошло, платить не за что. Он остаётся в силе — ни один статус, кроме
терминального, баллов не даёт.

Новое основание — статус `completed` **вместе с обязательной итоговой суммой**.
Заявка без итоговой суммы покупкой не становится: именно ввод суммы менеджером
превращает намерение в факт. Оценочный `estimated_total` для начислений не
используется нигде и никогда.

`cart-and-loyalty.md` правится в этой же работе: формулировка «автоматики нет»
станет ложью в момент выкатки.

# Часть 1. Факт покупки

## 1.1 Данные

| что | тип | зачем |
|---|---|---|
| `leads.final_total` | `Numeric(12,2)`, nullable | фактическая сумма сделки. NULL у всех незавершённых заявок |
| `leads.completion_seq` | `Integer`, default 0 | счётчик входов в `completed`, растёт на каждом входе |

`final_total` **не значение по умолчанию от `estimated_total`**, а отдельное
поле. Админка подставляет оценку в форму как подсказку, но в базу попадает то,
что менеджер подтвердил. Разница видна: если поля совпадут, это будет означать
«менеджер согласился», а не «никто не смотрел».

### Зачем `completion_seq` — не пропускать

Ключ идемпотентности начисления выводится из заявки. Если ключом будет
`lead_<id>_purchase`, то сценарий «завершили → откатили → завершили снова»
сломается молча: `record()` найдёт операцию с этим ключом и **вернёт старую
вместо новой**, то есть повторное завершение не начислит ничего, а баллы
останутся откаченными. Ошибка не выдаст себя ничем — ни исключения, ни лога.

Поэтому ключи включают номер попытки: `lead_<id>_<seq>_purchase`. Счётчик
инкрементируется при каждом входе в `completed`.

## 1.2 Переход в `completed`

Точка встройки — `PATCH /leads/{lead_id}` в `api/admin_crm.py:182`. Там уже
есть история статусов, аудит `lead_status_changed` и уведомление покупателю;
начисление встаёт туда же, в ту же транзакцию.

Правила:

1. переход в `completed` **без `final_total` отклоняется** с 400. Это не
   валидация ради валидации: заявка без суммы не является покупкой, и
   пропустить её значит вернуться к начислению за намерение;
2. `final_total` должен быть > 0;
3. `completion_seq` увеличивается на единицу **до** начислений;
4. проводится `loyalty.record(kind='purchase', amount=final_total)` с ключом
   `lead_<id>_<seq>_purchase`. Ставка берётся из уровня покупателя, как и
   сейчас, — эта часть `record()` не меняется;
5. вызывается `referral.payout_for_lead(...)` (часть 3);
6. заявка без `user_id` (заведена менеджером вручную, покупателя в системе нет)
   начислений не порождает и ошибкой не является;
7. при `auto_accrual_enabled = false` (часть 4) шаги 4 и 5 пропускаются
   целиком, а шаги 1–3 выполняются: требование итоговой суммы и счётчик
   попыток — свойства самой заявки, а не начислений. Иначе после включения
   рубильника у части завершённых сделок не оказалось бы суммы.

## 1.3 Уход из `completed` — откат

Любой переход из `completed` в другой статус откатывает всё, что было начислено
по этой заявке на текущем `completion_seq`:

- обратные операции проводятся с `kind='correction'` и комментарием, где назван
  номер заявки и причина («заявка 42 вышла из статуса „завершена“»);
- ключи — `lead_<id>_<seq>_purchase_revert` и так далее по каждой операции;
- откатываются **все три** возможных начисления: кэшбек покупателю, процент
  пригласившему, приветственные баллы приглашённому.

### Защита от отрицательного баланса мешает откату — и должна быть ослаблена

В `record()` стоит проверка:

```python
if current["balance"] + int(points) < 0:
    raise LoyaltyError(...)
```

Она применяется ко **всем** видам операций. Для списания это правильно: нельзя
потратить больше, чем есть. Для отката — фатально: если человек успел потратить
начисленное, корректировка не пройдёт, и мы останемся с балансом, полученным за
несостоявшуюся сделку. Ровно этим и будет пользоваться накрутка.

**Решение: `kind='correction'` разрешено уводить баланс в минус.** Отрицательный
баланс честнее молчания — он виден и в админке, и человеку, и означает ровно то,
что означает: баллы выданы за то, чего не было, и погашаются из будущих
начислений.

Это единственное изменение в самом `record()`, кроме описанного в 3.3.

# Часть 2. Реферальная связь

## 2.1 Данные

| что | тип | зачем |
|---|---|---|
| `users.referral_code` | `String(12)`, unique, nullable | личный код. Алфавит — `A-Za-z0-9_-`, тот же, что у рекламных меток: ровно то, что Telegram пропускает в `startapp` |
| `users.referred_by_user_id` | FK `users.id`, nullable, `ON DELETE SET NULL` | кто привёл. Ставится ОДИН раз при создании и никогда не переписывается |
| `ad_touches.kind` | `String(8)`, default `'ad'` | строка первого касания учится хранить не только рекламу: `'ad'` или `'ref'` |

`referral_code` выдаётся лениво — при первом открытии экрана приглашений, а не
всем 33 существующим пользователям разом. Код из 8 символов, генерируется
случайно, коллизия ловится уникальным индексом и вызывает повторную генерацию
(не проверкой «сначала посмотрим» — это гонка).

**Все три изменения схемы идут в `REQUIRED_SCHEMA`** в
`app/scripts/bot_polling.py`: обе колонки `users` и таблица `ad_touches`. Без
этого деплой валит бота с `UndefinedColumn` — грабли, о которых предупреждает
комментарий в самом файле. Список смыкается с мини-миграциями `main.py` тестом
`test_required_schema_covers_every_mini_migration_column`.

## 2.2 Ссылка

Формат: `t.me/<bot>?start=ref_<код>` — 4 символа префикса плюс 8 кода. Лимит
Telegram на start-параметр — 64 символа; у рекламных ссылок он выбран под ноль
(`ad_` + 40 + `_product_` + 12), у реферальных остаётся большой запас.

**Ведём в чат, а не в Mini App, сознательно.** Вход по `?startapp=` не даёт боту
права писать человеку: вся машинерия догона (`services/notifications.py`) для
таких пользователей молчит навсегда. Приглашённый друг остался бы без
напоминаний о корзине и без статусов заявки — это половина ценности приложения.
Та же причина, по которой в чат ведут платный трафик.

Разбор — `parse_ref_payload` рядом с `parse_ad_payload` в
`services/telegram_bot.py`, с тем же allowlist-подходом: явный перечень
символов, а не `isalnum()` (последний пропускает юникод).

## 2.3 Захват связи

Ветка в `_get_or_create_user` (`api/auth.py`) рядом с рекламной, по тем же
правилам:

1. **только при создании пользователя.** Повторный заход по чужой ссылке не
   имеет права переписать связь — как и `acquisition_source`;
2. приоритет у `start_param`, он точнее и приходит в том же запросе;
3. если метки в `start_param` нет — смотрим первое касание в `ad_touches` с
   `kind='ref'`. Telegram не прокидывает `start_param` в Mini App, открытый
   web_app-кнопкой из чата, и по ссылке `?start=ref_*` метка может дойти только
   так;
4. код резолвится в пользователя. Не нашёлся — связи нет, ошибки нет;
5. **самоприглашение отсекается** сравнением id. Новый пользователь своего кода
   ещё не имеет, но проверка стоит явно: она дешёвая, а полагаться на
   «этого не может случиться» в денежной механике нельзя;
6. пишется `referred_by_user_id`, `acquisition_source = 'ref_<код>'` и событие
   `referral_signup`.

`acquisition_source` заполняется тем же форматом, что рекламные метки, чтобы
фильтр админки по источнику работал без изменений.

# Часть 3. Выплаты

## 3.1 Кому и сколько

| кому | сколько | когда |
|---|---|---|
| пригласившему | `referral_rate_bps` от `final_total`, по умолчанию 1% | при каждой завершённой сделке приглашённого, бессрочно |
| приглашённому | `welcome_bonus_points`, по умолчанию 1000 | один раз, при его ПЕРВОЙ завершённой сделке |
| покупателю | обычный кэшбек по уровню | всегда (часть 1) |

Оба числа — **настройки** (часть 4), а не константы в коде. «1%» и «1000» ниже
по тексту означают значения по умолчанию; читать их как жёстко зашитые нельзя.

Обе выплаты проводятся видом `kind='referral'` и различаются комментарием
(«1% с покупки …» / «приветственные баллы за первую покупку»). Один вид, а не
два, потому что в отчёте это одна статья расходов — стоимость привлечения через
рефералов; разделять её на две строки незачем, а вид операции — не место для
подвида.

**`LOYALTY_KINDS` расширяется значением `'referral'`** (`models/loyalty.py:34`).
Это изменение схемы, хоть и без миграции: `_validate()` отвергает неизвестный
вид, и без правки списка ни одна выплата не пройдёт. Существующий `'bonus'` не
переиспользуется: он означает ручной подарок менеджера, и смешивать его с
автоматическими выплатами значит потерять возможность посчитать любую из двух
величин отдельно.

Балл равен рублю: `points_for(amount, rate_bps) = amount × rate_bps ÷ 10000`.
На покупке в 100 000 ₽ пригласивший получает 1000 баллов, сам покупатель на
уровне «Старт» — 250.

«Первая покупка» определяется как «число операций `kind='purchase'` у этого
пользователя равно единице» — то есть считается уже после проведения текущей.

## 3.2 Где живёт логика

Новый `services/referral.py`, функция `payout_for_lead(db, lead, seq)`,
вызывается из `admin_crm.py` **после** успешного `record(kind='purchase')`.

`record()` остаётся тем, чем был: примитивом журнала, который умеет провести
операцию и больше ничего не знает. Реферальные правила живут снаружи,
тестируются отдельно и не могут вызвать сами себя: выплата имеет
`kind='referral'`, а триггером служит только `kind='purchase'`.

Один уровень вверх и никаких цепочек. Если A привёл B, а B привёл C, то с
покупки C получает только B. Многоуровневость — это пирамида, и её здесь нет.

## 3.3 Правила проведения

- `kind='referral'`, **`amount=None`**. Оборот не растёт: иначе уровень можно
  было бы поднять, никогда ничего не купив, а `amount` в журнале зарезервирован
  за покупками (`lifetime_spent = SUM(amount) WHERE kind='purchase'`);
- ставка сохраняется в `rate_bps` операции — снапшот на момент выплаты, ровно
  как у кэшбека. Через год будет видно, по какому проценту платили. Для этого
  `record()` учится принимать `rate_bps` явно: сейчас он ставится только для
  `kind='purchase'` и иначе жёстко `None`;
- ключи идемпотентности: `lead_<id>_<seq>_referral` и
  `lead_<id>_<seq>_welcome`. Двойное сохранение статуса не удвоит выплату;
- **если 1% округляется в ноль — выплаты нет вовсе.** `record()` запрещает
  операции на ноль баллов, и это не ошибка, которую надо обойти: на покупке
  дешевле 100 ₽ платить нечего;
- у приглашённого нет пригласившего — не делаем ничего, это норма.

## 3.4 Уведомления

Пригласившему уходит сообщение в бот: «Ваш друг забрал покупку, вам начислено N
баллов». Через существующий `services/notifications.py` с `dedupe_key`,
привязанным к заявке и попытке, — та же схема, что у статусов заявки.

Приглашённому отдельного сообщения не нужно: он и так получает уведомление о
статусе заявки, и в нём будет видно начисление.

# Часть 4. Настройки в админке

## 4.1 Хранилище

Таблица `loyalty_settings` в одну строку (`id=1`), с явными колонками:

| колонка | тип | по умолчанию | смысл |
|---|---|---|---|
| `referral_rate_bps` | `Integer` | 100 | процент пригласившему, в сотых процента |
| `welcome_bonus_points` | `Integer` | 1000 | приветственные баллы приглашённому |
| `auto_accrual_enabled` | `Boolean` | true | главный рубильник автоначисления |

Явные колонки, а не универсальный «ключ-значение»: последний не типизируется,
не валидируется и через полгода содержит строку `"1%"` там, где код ждёт число.
Настроек три, и растут они медленнее, чем код вокруг них.

Строка создаётся при старте вместе с остальной схемой; отсутствие строки
трактуется как значения по умолчанию, а не как ошибка.

## 4.2 Рубильник

`auto_accrual_enabled = false` останавливает **все** автоматические начисления,
включая кэшбек покупателю. Ручное начисление из карточки клиента продолжает
работать — это путь отхода, если механика поведёт себя не так, как ожидалось.

Изменение любой настройки пишется в аудит: кто, когда, с какого значения на
какое.

## 4.3 Экран

Раздел «Лояльность» в админке: три поля, кнопка сохранения, текущие значения.
Ставка отображается процентами (`1%`), хранится в сотых (`100`) — как в
программе лояльности.

# Часть 5. Наблюдаемость и антифрод

## 5.1 «Кто кого привёл»

Раздел админки со списком пар: пригласивший, приглашённый, дата регистрации,
число завершённых сделок, сумма выплат. Сортировка по сумме выплат — накрутка
всплывает наверх сама.

## 5.2 Сигналы, которые видно без анализа

В карточке пригласившего показываются рядом:

- сколько людей пришло по его ссылке;
- сколько из них дошли до завершённой сделки;
- сколько баллов он получил и сколько потратил.

Схема «десять приглашённых, десять сделок, ноль трат» выглядит иначе, чем
органика, и это видно глазом без отдельного детектора.

## 5.3 Чего эти меры НЕ дают — читать обязательно

**Никакой код не отличит настоящую покупку от проведённой по просьбе.** Статус
`completed` и итоговую сумму ставит человек. Если менеджер проведёт сделку,
которой не было, система заплатит процент и будет права по всем своим правилам.

Предохранители дают три вещи: запрет очевидного (самоприглашение), видимость
(списки и суммы) и обратимость (откат при уходе из `completed`). Последним
рубежом остаётся тот, кто нажимает кнопку. Это ограничение конструкции, а не
недоделка: автоматизировать доверие к менеджеру нечем, пока в системе нет
собственного приёма платежей.

# 6. Что видит пользователь

Экран приглашений в профиле:

- личная ссылка и кнопка «Поделиться» — через готовый `lib/share.ts`, который
  уже умеет отдавать deep link вместо внутреннего адреса Mini App (делиться
  внутренним адресом нельзя: получатель попадёт в браузер без
  Telegram-авторизации);
- сколько людей пришло, сколько баллов принесли;
- **условия названы полностью и заранее**: 1% с каждой покупки друга, 1000
  баллов другу за первую покупку, баллы приходят после того, как друг забрал
  заказ. Роудмап обещает «без условий, которые видно только в конце» — прятать
  их в самой фиче было бы прямым нарушением обещания.

## 6.1 Долг: текст в роудмапе

Карточка `referral` в `frontend/src/lib/roadmap.ts` обещает разовое начисление
за первую покупку друга. Механика теперь другая — бессрочный процент. Текст
переписывается в этой же работе, иначе приложение врёт пользователю с первого
дня.

Правки текста, а не структуры: карточка остаётся одна, список роудмапа общий на
три шторки.

# 7. Чего в этой работе НЕТ

- **многоуровневых рефералов** — один уровень вверх, см. 3.2;
- **вывода баллов в деньги** — баллы тратятся внутри магазина, как и сейчас;
- **промокодов и купонов** — отдельная механика, реферальной не нужна;
- **собственного приёма платежей** — его нет в роудмапе намеренно, и эта работа
  его не приближает;
- **автоматического детектора накрутки** — только видимость, см. 5.3;
- **массовой выдачи кодов** существующим 33 пользователям — код появляется при
  первом открытии экрана.

# 8. Порядок работ

Часть 1 обязана уехать первой и может уехать одна: автоматический кэшбек по
завершённой сделке полезен сам по себе и не зависит ни от чего в частях 2–5.

1. **Факт покупки** — `final_total`, `completion_seq`, начисление и откат,
   ослабление защиты баланса для корректировок;
2. **Настройки** — таблица, рубильник, экран. Раньше выплат, чтобы рубильник
   существовал до того, как появится что выключать;
3. **Реферальная связь** — колонки, `REQUIRED_SCHEMA`, разбор ссылки, захват;
4. **Выплаты** — `services/referral.py`, уведомление;
5. **Экран в профиле** и текст роудмапа;
6. **Наблюдаемость** — списки в админке.

# 9. Риски

**Бессрочное обязательство.** Процент капает годами. Через год у активного
пригласившего может идти доход с десятка людей. Это осознанный выбор владельца
от 07.09; рубильник в настройках — способ остановить механику, но уже выданные
баллы он не отзовёт.

**Отрицательный баланс после отката.** Штатное состояние, а не сбой (см. 1.3).
Админка должна показывать его спокойно и понятно, а не как ошибку.

**Менеджер — последний рубеж.** См. 5.3.

**Изменение `record()`.** Две правки в функции, через которую проходят все
операции со счётом: явный `rate_bps` и разрешение минуса для корректировок.
Обе покрываются тестами до изменения поведения.

# 10. Проверки

```bash
cd backend && python -m pytest -q
cd frontend && npx tsc --noEmit && npx vitest run && npm run build
cd admin && npx tsc --noEmit && npm run build
```

Отдельно обязательно:

- `test_required_schema_covers_every_mini_migration_column` — держит список
  колонок бота сомкнутым с мини-миграциями;
- тест на сценарий «завершили → откатили → завершили снова»: второе завершение
  обязано начислить заново, а не вернуть старую операцию по совпавшему ключу;
- тест на откат при потраченных баллах: корректировка проходит и уводит баланс
  в минус;
- тест на самоприглашение;
- тест на нулевой процент: покупка, с которой 1% округляется в ноль, не создаёт
  операции и не падает.

Чистая арифметика (процент, приветственный бонус, определение первой покупки)
выносится в функции без БД и покрывается обычными тестами — как `points_for`,
`cartMath` и `navTiles`.
