# Ось «Бренды» на главной и тумблер «Каталог / AI» в поиске

Дата: 2026-07-28
Статус: утверждён, готов к планированию

## Задача

Две вещи, которые пользователь должен получить на витрине:

1. Навигацию по главной можно переключать между **категориями** и **брендами**.
2. Строку поиска можно переключать между **обычным поиском по каталогу** и
   **AI-подбором**.

Повод для первой — реальный дефект на проде: после перевода навигации на данные
(`dd960df`) плитка «Dyson» была скрыта как пустая, потому что в БД она заведена
как `action_type=category, action_value=dyson`, а категории `dyson` не
существует. Товары при этом есть: 50 штук, они лежат в `красота` и
`бытовая техника` под брендом `Dyson`. Крупнейший после Apple бренд магазина
пропал из навигации целиком.

## Что уже готово и не требует работы

- `ACTION_TYPES` в `backend/app/models/home.py` содержит `brand`.
- `GET /api/catalog/list` принимает `?brand=` и сравнивает точным равенством.
- `GET /api/catalog/brands` отдаёт список брендов (используется фильтром каталога).
- `actionRoute` во фронте маршрутизирует `brand` в `/catalog?brand=`.
- `catalog_nav.brand_counts()` уже считает `{бренд: количество активных товаров}`.

Отсутствует только ось навигации поверх этих данных и сами тумблеры.

## Решение

### 1. Бэкенд: `list_brands()` и вторая ось в `GET /home`

В `services/catalog_nav.py` добавляется `list_brands(db) -> list[dict]` —
зеркало `list_categories()` поверх существующего `brand_counts()`:

- элемент: `{key, label, icon, count}`;
- `key` — значение `Product.brand` как оно лежит в БД (фильтр `?brand=`
  сравнивает точным равенством, поэтому нормализация здесь сломала бы переход);
- `label` — то же значение (у брендов собственный регистр, `category_label()`
  здесь неуместен);
- порядок — по `count` убыв., затем по имени: порядок обязан быть
  детерминированным, иначе плитки прыгают между запросами при равных счётчиках;
- бренда без активных товаров в выдаче нет — как и пустой категории.

Иконка — единственное, что нельзя вывести из данных. Добавляется небольшой
`BRAND_ICONS` для известных брендов, для остальных `FALLBACK_ICON`. Это
оформление, **а не список брендов**: незнакомый бренд попадает в навигацию без
записи в словаре.

`GET /home` начинает отдавать `{banners, categories, brands}`.

Правило раскладки по осям:

| плитка | ось |
|---|---|
| `action_type == "brand"` | Бренды |
| всё остальное (`category`, `search`, `collection`, `ai`, `product`, `external`) | Категории |

Промо-плитки не переезжают и не образуют третью корзину.

Для каждой оси действуют те же правила, что уже описаны в CLAUDE.md:

- плитка, за которой нет товаров, на главную не выходит (`has_products()`);
- бренд, которого админ не касался, добавляется сам (слияние с `list_brands()`);
- `is_active=False` — осознанное «скрыть», автодобавление её не воскрешает.

Автодобавленные бренды получают отрицательные id со смещением (`-(1000+i)`) и
`position` от 2000, чтобы не пересекаться с автодобавленными категориями.

Совместимость: ключ `categories` не меняет ни формы, ни смысла; `brands`
добавляется рядом. Фронт предыдущей версии, поднятый из кэша браузера,
продолжает работать.

### 2. Прод-данные

После деплоя — две строки, выполняются только после явного подтверждения:

```sql
UPDATE home_categories SET action_type='brand', action_value='Dyson' WHERE action_value='dyson';
DELETE FROM home_categories WHERE action_type='category' AND action_value='аксессуары';
```

`UPDATE`, а не `DELETE` для Dyson: строка хранит эмодзи, градиент и позицию 6 —
оформление, которое иначе пришлось бы заводить заново. «Аксессуары» удаляется:
за ней нет и не было товаров. «Скидки» (`__sale__`) не трогаем — плитка вернётся
сама, когда появится хотя бы один товар с `on_sale` (сейчас их 0).

Без SQL Dyson всё равно появится на оси брендов автоматически — но с дефолтным
оформлением и в конце списка.

### 3. Админка

`ACTION_LABELS` в `admin/src/HomeAdmin.tsx` не содержит `brand`, хотя бэкенд
принимает этот тип с самого начала: создать бренд-плитку через интерфейс
сегодня невозможно. Добавляется `brand: "Бренд"` и уточняется плейсхолдер поля
«Значение действия».

### 4. Фронт

Оба тумблера — один компонент `components/SegmentedToggle.tsx`: сегментированный
переключатель на два положения, `role="tablist"`, `aria-selected`, управление
стрелками, тач-таргет 44px, фиксированная высота (переключение не должно
дёргать вёрстку).

**Тумблер «Категории / Бренды»** — над рядом hero-чипов на главной.

Отдельной сетки плиток на главной нет: навигация по разделам — это ряд
hero-чипов (`Home.tsx`, максимум 6) и список в desktop-сайдбаре. Ось общая для
обеих поверхностей — одно состояние в `Home`, прокинутое в `HomeSidebar`, иначе
hero показывал бы бренды, а сайдбар рядом с ним категории. Подпись сайдбара
(«Категории»/«Бренды») и хвостовая кнопка ряда («Все категории →»/«Все
бренды →») меняются вместе с осью.

- состояние локальное, по умолчанию «Категории»;
- без URL-параметра и без localStorage: сохранение не требовалось, а лишнее
  состояние нужно тестировать и синхронизировать;
- при пустом `brands` тумблер не рендерится вовсе — переключатель во вкладку без
  содержимого хуже отсутствующего переключателя;
- переключение пишет событие аналитики `home_axis_switched` с текущей осью.

**Тумблер «Каталог / AI»** — в строке поиска:

- `Enter` и кнопка отправки ведут либо в `/catalog?query=`, либо в `/ai?q=`;
- введённый текст при переключении режима сохраняется (состояние живёт над
  инпутом);
- плейсхолдер меняется вместе с режимом: «Поиск по каталогу» ⟷ «Опишите, что
  нужно — подберём»;
- режим не сохраняется между визитами, по умолчанию «Каталог».

Логика маршрута выносится в чистую функцию `searchRoute(mode, query)` — сейчас
одинаковый обработчик `Enter` продублирован в `Home.tsx`, `Catalog.tsx` и
`DesktopHeader.tsx`, и четвёртая копия уже с режимами нежизнеспособна. Чистая
функция тестируется без DOM, как `searchHistory` и `categoryCache`.

**Границы v1:** тумблер поиска ставится на главную и в desktop-шапку — это одна
и та же строка поиска в двух раскладках. Собственный поиск внутри `/catalog` не
трогается: пользователь там уже в каталоге, уводить его в чат посреди подбора
фильтров сомнительно. Компонент останется готовым, если решение изменится.

Кэш в localStorage для брендов не заводится: плитки брендов приходят из `/home`,
а тумблер невозможно нажать раньше, чем `/home` ответит. Мгновенная отрисовка
решала бы там несуществующую проблему.

## Тесты

Тестов на `GET /home` не было вплоть до `dd960df` — именно поэтому мёртвые
плитки дожили до прода. Сейчас в `tests/test_catalog_nav.py` их десяток; новые
дописываются туда же, к существующим правилам видимости.

Фронт тестируется только на уровне чистых функций: `vitest.config.ts` собирает
`src/**/*.test.ts` в окружении `node`, без DOM. Это осознанное решение проекта,
и ради двух тумблеров jsdom и testing-library не подключаются. Поэтому вся
решающая логика выносится из компонентов в чистые функции, а сам рендер
проверяется в браузере.

**pytest:**

- `list_brands()`: пустой каталог → `[]`; бренд без активных товаров не попадает;
  детерминированный порядок при равных счётчиках; fallback-иконка для
  незнакомого бренда.
- `GET /home`: `brands` содержит бренд с ненулевым счётчиком; курируемая
  бренд-плитка с `is_active=False` не воскресает; бренд-плитка с несуществующим
  брендом скрыта; `category`-плитка не протекает в `brands` и наоборот; форма
  ключа `categories` не изменилась (регрессия).

**vitest (чистые функции, без DOM):**

- `searchRoute`: оба режима, пустой запрос, экранирование кириллицы и `&`.
- `navTiles`: сборка чипов для каждой оси из ответа `/home`; ось «бренды» при
  пустом `brands` даёт пустой список (по нему компонент прячет тумблер);
  фолбэк на кэш категорий работает только для оси категорий.

**Перед сдачей** — полный прогон по CLAUDE.md: `pytest -q` в backend,
`tsc --noEmit` + `vitest run` + `build` во фронте, `tsc --noEmit` + `build` в
админке.

## Что осталось за рамками

- Тумблер поиска внутри `/catalog`.
- Сохранение выбранной оси и режима поиска между визитами.
- Логотипы брендов вместо эмодзи.
- Открытые хвосты проекта, к этой работе не относящиеся: `Enter` в AI-чате,
  фильтры по региону/памяти/размеру, свободный текст в боте, латентность LLM,
  гейтвей для Anthropic в открытом регионе.
