## 3. Архитектурное решение корзины

### Корзина
Серверная, привязана к существующему `users.id` из Telegram-авторизации. Новой
идентичности не вводится — тот же подход, что у избранного.

- `carts` — одна **активная** корзина на пользователя. Инвариант держит частичный
  уникальный индекс `uq_carts_active_user (user_id) WHERE status='active'`, а не
  проверка в коде: гонка двух параллельных «добавить» иначе создаёт две корзины,
  и половина товаров теряется.
- `cart_items` — уникальность `(cart_id, product_id)`; повторное добавление
  увеличивает количество.
- `added_price` — **снапшот на момент добавления, а не актуальная цена**. Сумма
  всегда считается по `products.price`; расхождение показывается пользователю
  («Цена обновилась»).
- Склад корзиной **не трогается**: `products.stock` — это склад, а не резерв.

### Заявка — вариант A (расширение существующего `Lead`)

Выбран не по эстетике схемы, а по цене интеграции. На `Lead` уже висят шесть
потребителей: `/leads/my`, экран «Заявки» Mini App, список админки, фильтры,
дашборд, аналитика источников. Отдельная сущность `CartOrder` потребовала бы
продублировать все шесть вручную — а это ровно тот путь, на котором возникает
худший отказ этого релиза: пользователь видит «отправлено», менеджер заявки не
видит.

- `Lead` получил необязательные `items_count`, `estimated_total`, `currency`,
  `idempotency_key`. Существующие одиночные заявки их не заполняют и работают
  без изменений.
- `lead_items` — позиции со **снапшотами** (`sku/title/price/quantity/line_total/
  availability`). `product_id` — `ON DELETE SET NULL`: удаление товара не имеет
  права утащить позиции уже отправленной заявки. В живой корзине наоборот,
  `CASCADE`.
- `lead_type='cart'`, `source='telegram_mini_app_cart'`.

### Режим доступности

В проекте не было понятия «режим доступности» — только `is_active`, `in_stock`,
`stock`, `is_limited`. Правила ТЗ (`out_of_stock`, `preorder`) выразить этими
флагами нельзя.

`backend/app/services/availability.py` — единственный резолвер:

| условие | режим | можно заказать |
|---|---|---|
| `is_active=false` | `unavailable` | нет |
| явная колонка `products.availability_mode` | она и есть | по режиму |
| `in_stock=false` | `on_request` | да |
| `in_stock=true, is_limited=true` | `limited` (кол-во ≤ `stock`) | да |
| иначе | `in_stock` | да |

`products.availability_mode` **nullable, по умолчанию NULL** = вывод из флагов,
то есть поведение существующих 217 товаров прода не меняется ни на шаг.
Проверено: после миграции `availability_mode IS NOT NULL` — 0 строк.

### Идемпотентность

`idempotency_key` уникален **в пределах пользователя**
(`uq_leads_user_idempotency (user_id, idempotency_key) WHERE idempotency_key IS NOT NULL`).
Глобально уникальный ключ позволял бы чужому клиенту занять значение и сломать
checkout соседу. Клиент генерирует ключ на попытку отправки и переиспользует его
при ретрае до успеха.

## 4. User flow

```
Каталог / Главная / Избранное / История
  → «Добавить» на карточке → степпер −  N  +
  → sticky-панель над навигацией: «N товаров · сумма» + «Корзина →»
  → /cart: состав, цены, наличие, предупреждения
  → изменить количество / удалить / очистить
  → имя, телефон, способ получения, комментарий, согласие
  → «Отправить заявку»
  → «Заявка №N отправлена» + «Мои заявки» / «Продолжить покупки» / «Написать менеджеру»
  → админка → Заявки → строка типа «Корзина» → «Открыть»
```

Карточка товара: «Добавить в корзину» → степпер + «Перейти в корзину».
«Купить сейчас» добавляет ТОЛЬКО этот товар и открывает оформление —
**заявку не отправляет**: одно случайное нажатие не должно создавать заявку.

## 6. Миграции

Alembic в проекте нет. Схема применяется на старте backend:
`Base.metadata.create_all()` + идемпотентные `ALTER … IF NOT EXISTS` в
`_apply_demo_migrations()` (`backend/app/main.py`). Новая миграция следует тому же
правилу и **ничего не удаляет и не конвертирует**.

Создаются `create_all`: `carts`, `cart_items`, `lead_items`.

Добавляются `ALTER`:
```sql
ALTER TABLE leads ADD COLUMN IF NOT EXISTS items_count INTEGER DEFAULT 0;
ALTER TABLE leads ADD COLUMN IF NOT EXISTS estimated_total NUMERIC(12,2);
ALTER TABLE leads ADD COLUMN IF NOT EXISTS currency VARCHAR(8) DEFAULT 'RUB';
ALTER TABLE leads ADD COLUMN IF NOT EXISTS idempotency_key VARCHAR(64);
UPDATE leads SET items_count = 0 WHERE items_count IS NULL;
CREATE INDEX IF NOT EXISTS ix_leads_idempotency_key ON leads (idempotency_key);
CREATE UNIQUE INDEX IF NOT EXISTS uq_leads_user_idempotency
  ON leads (user_id, idempotency_key) WHERE idempotency_key IS NOT NULL;
ALTER TABLE products ADD COLUMN IF NOT EXISTS availability_mode VARCHAR(20);
```

### Проверено

| проверка | результат |
|---|---|
| Чистая БД (`migtest`) | таблицы, колонки и индексы созданы |
| Копия актуальной схемы с данными (локальная demo, 217 товаров / 5 заявок) | данные целы, все 5 заявок получили `items_count=0`, `currency='RUB'`, `estimated_total=NULL` |
| Rollback (SQL ниже) | выполнен, объекты удалены |
| Повторное применение после rollback | таблицы созданы заново, ошибок нет |
| `availability_mode IS NOT NULL` после миграции | 0 строк — поведение товаров не изменилось |

### Rollback

```sql
BEGIN;
DROP TABLE IF EXISTS lead_items;
DROP TABLE IF EXISTS cart_items;
DROP TABLE IF EXISTS carts;
DROP INDEX IF EXISTS uq_leads_user_idempotency;
DROP INDEX IF EXISTS ix_leads_idempotency_key;
ALTER TABLE leads
  DROP COLUMN IF EXISTS items_count,
  DROP COLUMN IF EXISTS estimated_total,
  DROP COLUMN IF EXISTS currency,
  DROP COLUMN IF EXISTS idempotency_key;
ALTER TABLE products DROP COLUMN IF EXISTS availability_mode;
COMMIT;
```

Rollback удаляет **только** новые объекты. Существующие заявки, товары, SKU,
цены и фото не затрагиваются. Уже отправленные заявки-корзины после отката
останутся в `leads` без позиций — их состав будет потерян, поэтому откат имеет
смысл только до появления таких заявок на проде.

## 7. API

Все маршруты под `get_current_user`; корзина принадлежит пользователю и чужую
нельзя ни прочитать, ни изменить (фильтр по `user_id` в каждом запросе).

| метод | путь | назначение |
|---|---|---|
| GET | `/api/cart` | состояние корзины с актуальными ценами и наличием |
| POST | `/api/cart/items` | добавить товар (повтор увеличивает количество) |
| PATCH | `/api/cart/items/{item_id}` | изменить количество (`0` = удалить) |
| DELETE | `/api/cart/items/{item_id}` | удалить позицию |
| DELETE | `/api/cart` | очистить корзину |
| POST | `/api/cart/checkout` | отправить одну общую заявку |

Каждая мутация возвращает **полное** состояние корзины — клиенту не нужно
пересчитывать суммы самому.

Админка:

| метод | путь | назначение |
|---|---|---|
| GET | `/api/admin/leads/{lead_id}` | детали заявки: снапшот + актуальные цены + история статусов |

Коды ошибок (`detail.code`): `not_found`, `not_orderable`, `items_unavailable`,
`cart_full`, `empty_cart`, `consent_required`, `phone_required`.
`items_unavailable` возвращает список проблемных позиций — клиент показывает
конкретные строки, а не общее «что-то пошло не так».

## 8. Модель заявки

`Lead` (существующая таблица) + `lead_items`:

```
Lead: id, public_number (= «№id»), user_id, telegram_id, name, phone, username,
      lead_type='cart', source='telegram_mini_app_cart',
      delivery_method (pickup|delivery|consult), message,
      items_count, estimated_total, currency, idempotency_key,
      status, assigned_to, manager_comment, created_at, updated_at

LeadItem: lead_id, product_id (SET NULL), sku_snapshot, title_snapshot,
          price_snapshot, quantity, line_total, availability_snapshot,
          image_snapshot
```

**Статусы расширены аддитивно** до восьми:
`new, contacted, confirming, confirmed, in_progress, reserved, completed, cancelled`.
Требуемые ТЗ значения появились; старые пять остались рабочими, потому что
именно они стоят у существующих заявок. Второй словарь статусов для одного поля
не заводился: админка и витрина читают один список.

Отдельного счётчика `public_number` нет — `id` уже уникален и стабилен, а второй
номер пришлось бы синхронизировать.

## 9. Интеграция с админкой

- Раздел «Заявки» — таблица: номер, тип, дата, клиент, телефон, Telegram,
  позиции (`N поз. · M шт`), предварительная сумма, способ получения, статус,
  источник, менеджер, «Открыть».
- Фильтры: статус, тип (`Корзина`), источник (`Корзина`).
- Детальная модалка: все позиции с фото, SKU, названием и ценой **из снапшота**
  рядом с **актуальными** значениями каталога и разницей цены; пометки «товар
  удалён» / «скрыт с витрины»; предварительная сумма; контакты; комментарий;
  способ получения; даты; история статусов.
- Действия: статус, ответственный, внутренняя заметка (`manager_comment`),
  копирование состава в буфер, переход на товар витрины, диалог в Telegram
  (только при живом `username` — ссылка по числовому id не работает).
- Снапшот заявки менеджер изменить не может: правок состава в UI нет и API их не
  принимает.
- История статусов пишется в существующий журнал `audit_logs`
  (`action='lead_status_changed'`), а не в новую таблицу.
- Дашборд: заявки корзины входят в общий счётчик и в «сегодня» автоматически
  (та же таблица) + отдельная метрика «Из корзины». Аналитика источников
  показывает `telegram_mini_app_cart`.

## 16. Known limitations

1. **Production уже несёт эту ветку, но без правок приёмки** — см. §18. Это
   главное ограничение RC2, и решение по нему за вами.
2. **На проде работает код, не соответствующий ни одному коммиту** —
   синхронизировано дерево с незакоммиченными правками.
3. **Откат к предыдущим образам на проде невозможен** — они затёрты тегом
   `:latest`. Откат только пересборкой из git. Шаг с неизменяемыми тегами
   добавлен в план деплоя (§18a).
4. **Тестов админки в проекте нет** — ни одного, и этот релиз их не добавляет:
   тестового рантайма для admin не существует, его заведение — отдельная задача.
   UI админки проверен сквозным прогоном в браузере (вход, список, детали,
   смена статуса) и 14 backend-тестами её эндпоинтов.
5. **Component-тестов фронта нет.** В проекте нет `jsdom`/`@testing-library`, а
   добавление их меняет `package-lock`. Поэтому логика корзины вынесена в чистые
   модули (`cartMath`, `cart`) и покрыта 40 тестами, а связка с компонентами
   проверена сквозным прогоном на production-сборке.
6. **История статусов начинается с этого релиза.** У существующих заявок её нет:
   `audit_logs` раньше смены статусов не писал.
7. **`out_of_stock` и `preorder` не выводятся из данных** — их нужно проставить
   в админке (селект «Доступность»). По умолчанию всё работает ровно как раньше.
8. **Уведомлений менеджера нет** — см. §11.
9. **Корзина не сливается при смене устройства до входа** — гостевой корзины нет
   вовсе, всё требует авторизации (как и было в проекте).
10. **`estimated_total` не пересчитывается после создания заявки.** Это снапшот
    договорённости; актуальные цены видны рядом в админке.
11. **Локальная demo-БД содержит следы приёмки:** заявки №6 и №7 и три товара с
    демонстрационными режимами (`id=36 out_of_stock`, `id=38 preorder`,
    `id=39 is_limited`). На прод не влияет. Откат:
    `UPDATE products SET availability_mode=NULL WHERE id IN (36,38); UPDATE products SET is_limited=false WHERE id=39;`
12. **`/auth/admin/dev` — новая поверхность,** пусть и закрытая. Гейт серверный
    (`DEV_MODE=false` → 404, проверено на проде), пароль в маршруте не
    участвует, вход помечается в журнале отдельным subject. Но это маршрут,
    которого раньше не было, и его стоит держать в поле зрения при аудите.

## 17. Соответствие референсу

Совпадает: компактная строка бренда с действиями; одна строка поиска с
переключателем «Каталог / AI»; тумблер «Категории / Бренды»; одна строка чипов
категорий; одна компактная строка сценариев (iPhone, MacBook, Trade-In, Для
бизнеса, Опт); крупные баннеры в горизонтальной ленте; «Вы недавно смотрели»;
sticky-панель корзины с бейджем, количеством, суммой и кнопкой «Корзина →»;
нижняя навигация из пяти вкладок.

Расходится осознанно:

- **«Бесплатная доставка от 5 000 ₽» не выводится.** Такого правила backend не
  отдаёт, а придуманный порог — это обещание за счёт магазина. Вместо него —
  «Предварительно — итог подтвердит менеджер».
- **Кнопка добавления на карточке — компактная строка «Добавить», а не круглый
  «+» в углу.** ТЗ допускает оба варианта; строка фиксированной высоты
  гарантирует одинаковую высоту карточек в сетке и даёт больший тап-таргет на
  экране 360 px.
- **Меню «…» в шапке не добавлено** — ТЗ помечает его как «при необходимости»,
  а неработающая кнопка хуже отсутствующей. Вместо неё в том же ряду — кнопка
  корзины с бейджем (постоянный вход, иначе пустая корзина недостижима).

Утверждать попиксельное совпадение без скриншотов я не могу и не утверждаю.
